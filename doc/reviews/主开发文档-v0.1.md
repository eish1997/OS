# 个人 AI 工作台主开发文档

版本：0.1  
整理日期：2026 年 10 月 5 日  
状态：产品与架构基线，尚未完成运行原型  
读者：产品负责人、开发 Agent、后续参与开发与验证的人员

本文汇总全部产品讨论，作为后续需求拆分、架构设计、实现和验收的统一依据。已经确定使用 Pi 作为 Agent 执行底座；具体社区组件、数据结构和技术栈仍需通过原型验证。本文中的架构与开发顺序为实施建议，不代表已经实现或由用户逐项确认。

## 1 产品定义

构建一个以个人 AI 助手为统一协作入口的可扩展工作台。用户通过自然对话表达想法和需求，助手将意图转化为项目，组织工具和子代理推进工作，验证并呈现成果，将经验沉淀为可复用能力，并帮助用户制作和发布内容。

系统既承担日常工作，也帮助用户探索新方向、验证想法、发现机会。核心能力是可验证地修改和扩展自身：新增技能、接入工具、改进流程、开发界面和功能，经过验证后启用，并保留恢复路径。

长期目标是让有限的个人注意力支撑更多探索，形成持续积累的知识、工具、作品与对外影响。

## 2 用户背景与设计原则

用户不是专业开发者，主要借助 AI Agent 开发。兴趣方向多，经常从社媒发现开源项目，希望通过链接或自然描述让助手理解、试运行并接入自己的工作台。

产品应遵循以下原则：

- 用户表达目标即可，不要求提前理解专业术语或工具位置。
- 优先复用成熟组件，通过扩展集成能力，减少重复开发。
- 对话随时可用，项目成果与工作现场占据主要界面。
- 多个项目集中管理，各自拥有独立上下文和工作空间。
- Agent 操作与界面操作共享状态，完成声明必须关联真实成果。
- 文件和资产能备份、迁移、追溯，项目积累能够复用。
- 自主程度由权限、预算和验收标准约束。
- 内容输出从项目开始积累素材，并使用真实证据。
- 执行效率提升后，系统同时帮助用户管理注意力与项目优先级。

## 3 已确定的决策

| 决策 | 内容 |
| --- | --- |
| 执行底座 | 采用 Pi，优先保留官方内核，通过 SDK、RPC 和扩展集成 |
| 主要交互 | 自然对话，理解当前项目与选中对象，支持全局协调 |
| 页面骨架 | 主页展示项目库，每个项目打开为独立标签页 |
| 项目组织 | 集中管理，多项目可并行，项目资料和执行环境需隔离 |
| 执行主体 | 主助手统筹，按需使用子代理或代理群组 |
| 状态关系 | Agent 执行、界面操作、实际资产同步关联 |
| 扩展方式 | 接入工具和开源项目，积累技能，组合已有能力 |
| 自我修改 | 系统能开发自身能力和产品功能，验证后启用 |
| 输出范围 | 项目成果、文章、观点、短帖、视频脚本及发布素材 |
| 视觉方向 | 深色专业创作工具风格，浮动面板、成果预览、细线连接、克制状态色 |

尚未确定：产品名称、最终客户端技术、部署方式、模型配置、社区扩展版本、首个真实业务项目和发布渠道。

## 4 产品外在形态

### 4.1 主页与项目库

主页采用项目画廊或仓库列表，展示项目预览、简介、状态、最近活动与待决事项。支持搜索、分类、归档和创建项目。

主页包含收件入口，接收临时想法、链接、文件和日常需求。输入不完整时，助手先帮助梳理，避免立即创建大量无目标项目。

### 4.2 项目标签页

每个项目拥有独立标签页，保留当前工作现场和上下文。标签页包含目标、任务、资料、运行状态和成果，按项目类型提供合适视图。

| 类型 | 推荐视图 |
| --- | --- |
| 软件开发 | 产品预览、任务、变更、运行与测试结果 |
| 图片创作 | 素材库、画廊、编辑画布、版本对比 |
| 研究验证 | 来源、证据、实验、比较与结论 |
| 内容创作 | 素材、稿件、版本、渠道与发布状态 |

动态界面应读取统一项目数据，通过已注册操作执行动作。生成新布局时优先组合现有组件；新增可执行代码进入正常开发与验证流程。

### 4.3 随处可用的对话

对话入口可表现为底部浮动输入、快捷键、侧边浮层、对象操作入口，语音属于后续可扩展能力。

发送指令时传递当前项目、视图、选中资产及其版本。跨项目操作要明确目标对象，避免根据视觉位置猜测。

### 4.4 全局工作进展

集中展示运行中、等待用户、阻塞、失败和完成的任务。支持调整优先级、暂停、取消、恢复和查看日志。需要时展开子代理执行过程。

节点画布用于解释流程和依赖，时间线用于呈现历史；常规操作仍可通过对话完成，不要求用户手动搭建节点。

### 4.5 资产库与作品空间

资产库管理文件、来源、版本和跨项目引用。作品空间将项目证据转化为文章、短帖、图文、视频脚本等，并记录审核和发布结果。

## 5 工作闭环

### 5.1 从想法到成果

接收想法 → 明确目标与成功标准 → 搜集信息 → 制定有限投入的计划 → 执行 → 验证 → 交付 → 决定继续、调整或结束。

研究应针对相关来源开展，记录出处和时间，明确停止条件。“全网爬取”是用户愿景，实施时需要目标驱动的搜索、访问与证据筛选。

### 5.2 从成果到内容

项目启动时记录动机；执行时记录关键尝试、决策、截图和实验；结束时提炼结果、局限与用户观点。根据渠道生成内容版本，按照授权执行发布。

生成内容不得虚构用户经历、实验结果或个人观点。用户修改和外部反馈作为后续改进依据。

### 5.3 从项目到能力

已验证工具和有效方法沉淀为能力包。多个能力可以组合成新流程，例如生成图片 → 编辑图片 → 检查 → 输出。

项目合并需区分资料与历史合并、能力组合。默认保留来源关系，避免无记录地移动或覆盖资产。

### 5.4 主动发现机会

在用户指定的领域、来源和周期内收集变化，形成带依据的机会建议。主动研究、投入执行资源、对外发布分别设置授权范围。未请求持续监控时不默认启动长期后台采集。

## 6 推荐系统架构

### 6.1 产品层

负责项目主页、标签页、资产视图、动态页面、对话入口与进度展示。

### 6.2 工作管理层

负责项目、任务、优先级、依赖、预算、权限、暂停恢复和代理调度。保存系统业务状态，不依赖单次模型会话。

### 6.3 Agent 适配层

封装 Pi 的会话、消息、工具事件、执行控制和恢复接口。将执行事件转换为统一工作台事件，避免界面直接依赖社区扩展内部格式。

首版只接一个执行引擎，不提前实现多引擎系统，但保持适配边界。

### 6.4 工具与能力层

由 Pi 扩展、Skills、脚本、MCP 服务和外部应用组成。每项能力登记用途、输入输出、权限、依赖、版本与验证状态。

### 6.5 数据层

项目文件夹保存实际资产；持久化状态存储保存任务、运行、关系和索引。会话记录作为过程证据，不承担全部业务状态。

### 6.6 自我改进层

负责提出改进、创建候选版本、开发、测试、比较、发布和恢复。工作助手、开发执行与发布控制承担不同职责，可使用相同模型，但权限需区分。

## 7 Pi 与生态复用

Pi 作为 Agent 执行引擎，承担模型交互、工具调用、会话和扩展加载。它不是已经完成的项目管理产品，也不自动具备可靠自我进化。

| 组件 | 计划用途 | 状态 |
| --- | --- | --- |
| Pi SDK 或 RPC | 将 Agent 接入工作台，获取流式事件和执行结果 | 接口方案待验证 |
| pi-subagents | 委派任务和多代理工作流 | 社区候选，未选定版本 |
| pi-mcp-adapter | 接入 MCP 工具 | 社区候选，按需求接入 |
| Pi Skills 与扩展包 | 封装方法、工具和新增能力 | 确定采用的扩展方向 |

社区包需记录原始仓库、作者、许可证、固定版本、依赖和兼容结果。优先选单一子代理实现，避免混装同名分支。安装功能不等于取得新增权限。

模型选择通过配置实现。目标是支持用户希望使用的不同供应商模型；具体接口、认证、费用和可用性需核实。消费端 ChatGPT 或 Claude 产品的功能与模型 API 接入不可直接等同。

## 8 最小数据模型建议

| 对象 | 必要信息 |
| --- | --- |
| Project | 标识、名称、目标、验收标准、路径、状态、预算、策略 |
| Task | 项目、输入、预期输出、依赖、状态、负责人、验收结果 |
| Run | 执行标识、任务、会话、模型、环境、时间、费用、事件 |
| Agent | 角色、工具范围、模型配置、并发与委派限制 |
| Asset | 路径或外部引用、类型、来源、版本、项目与引用关系 |
| Capability | 名称、接口、依赖、权限、版本、验证与启用状态 |
| Change | 改进动机、基线、改动、评价、发布和恢复记录 |
| Publication | 素材、稿件、渠道版本、审核、授权和发布结果 |

建议使用稳定标识关联对象。文件重命名或视图变化不应破坏引用。敏感凭据独立存储，不写入普通项目文件、日志或能力包。

## 9 状态同步与执行契约

所有修改通过可记录的操作入口执行。操作至少包含项目、目标对象与版本、输入、执行标识、权限上下文和结果。

任务状态建议为：待安排、运行中、等待用户、阻塞、成功、失败、已取消。完成必须存在成果或可验证的操作结果。

界面通过事件流更新，重新打开后从持久化状态恢复。需要处理重复事件、断线重连、部分失败、重复提交和过期版本。

任务重试不应重复发布内容或重复产生外部写入。对外操作需要幂等或明确检测既有结果。

资产写入完成后才登记为可用。外部变化需检测并对账。用户手动修改和代理同时修改时应检测冲突，避免静默覆盖。

## 10 多项目与多代理

主助手掌握全局目标，调度器管理持久化任务。每个项目使用独立目录、会话和必要的运行环境。

子代理接收明确任务、限定输入、预期产物和验证标准。交接使用文件或结构化结果，不能只依赖自然语言“完成了”。

设置并发数、委派深度、预算和超时。存在依赖时顺序执行，独立任务才并行。同一文件或资源的并发写入通过隔离副本、锁定或合并控制。

暂停停止安排新任务；运行中操作能否中止取决于工具。取消、恢复与部分成果处理应有明确语义。首版优先实现受控委派，再扩展代理群组协作。

## 11 自我修改与持续改进

### 11.1 可修改范围

记忆、技能、提示词、工具适配器、任务流程、界面和产品功能可进入改进流程。Agent 运行机制的修改需要更严格的回归验证。

通过模型 API 改进系统，不意味着能够直接修改供应商模型权重。

### 11.2 改进流程

1. 根据用户需求、失败记录或重复工作提出改进。
2. 建立目标、基线、验收条件和投入上限。
3. 创建独立分支或副本，保存依赖与数据版本。
4. 开发候选版本，运行针对性测试。
5. 用保留任务比较旧版与新版，检查质量、成本与回归。
6. 在授权范围内启用，通过运行记录观察实际效果。
7. 失败时恢复，并保存改进结论。

运行中的主助手应继续可用。新插件或内核版本不得直接替换正在工作的环境。

### 11.3 稳定底座

启动、版本选择、权限上限、预算约束、备份恢复和发布控制保持稳定。Agent 可以提出修改，但普通工作任务不能自行绕过这些控制。

开发候选可以生成新测试，但不能在同一次改进中擅自改变用于判定通过的既定标准。验证模型的意见只是证据之一，关键行为优先使用客观测试。

### 11.4 评价方式

软件看运行行为与测试；研究看来源支持和不确定性；图片看规格、可用性与用户选择；文章看事实依据、表达偏好和审核反馈。

不存在能统一可靠判断所有任务的单一总分。评分需要展示维度、依据和未验证项。审美与观点保留用户最终判断。

## 12 开源项目接入流程

输入链接 → 检查用途、许可证、依赖与运行条件 → 建立隔离试验 → 最小运行 → 目标验证 → 封装适配 → 登记能力 → 接入视图 → 维护与升级。

记录版本、安装方法、环境、费用、凭据需求与失败情况。开源项目可能通过 CLI、SDK、HTTP 或 MCP 调用，不默认将所有源码合并进工作台。

## 13 视觉设计基线

用户提供五张参考，表达对深色专业工作台的偏好：

- 近黑画布和炭灰面板，边框细，层次清晰。
- 浮动面板与工具栏，适量玻璃质感。
- 大幅成果预览，文字简洁。
- 节点连接与时间线展示执行关系。
- 少量荧光绿强调操作，青色表示运行，橙色表示关注。

必须保证文字对比、状态识别和布局可用性。颜色以外使用图标或文字表达状态。动态页面使用统一设计基础。

现有图片为概念效果图，不是运行截图；其中名称、模型、状态与数据为示意。首版亮色方向已被用户否定，新版深色方向参考用户图片生成，但尚未得到逐项视觉确认。

## 14 开发阶段与验收

### 阶段一 验证 Pi 接入

接通模型、创建会话、调用工具、接收事件并展示成果。验证运行环境，特别是用户当前 Windows 环境下的社区组件兼容性。

验收：一次真实任务完成后，能从工作台查看产物、过程与失败原因，关闭重开后记录存在。

### 阶段二 建立项目工作台

实现主页、项目标签页、文件与资产管理、上下文对话和基础任务状态。优先开发固定可靠的页面，再增加动态视图。

验收：两个项目的上下文与文件隔离，切换标签页后助手指向正确项目，界面与资产同步。

### 阶段三 受控并行与工具扩展

接入选定子代理实现、依赖调度、预算和暂停恢复。按真实任务增加 MCP 或其他工具。

验收：两个独立任务并行，依赖任务按顺序执行，失败可定位，用户调整优先级生效。

### 阶段四 第一次自我升级

用户通过对话要求增加一个图片对比功能。Agent 在独立副本开发扩展与视图，验证、启用并演示恢复。

验收：新功能能从界面和对话使用，旧项目正常，验证记录可查看，恢复后系统可启动。

### 阶段五 内容输出闭环

积累项目素材，生成有来源的复盘文章或短帖，支持编辑与渠道版本。先完成导出和审核，再接实际发布接口。

验收：稿件能追溯真实素材，用户修改被保存，对外发布遵守授权且不会重复提交。

### 阶段六 主动发现与流程优化

在明确监控范围内发现机会，根据历史反馈改进技能和流程。逐步验证动态界面与更复杂代理群组。

验收：建议有依据，监控按约定运行，改进在保留任务上有收益，并且成本可控。

## 15 首版边界

首版目标是一个完整可用的闭环，不承诺全能、全网无边界采集或无限递归自我进化。

优先实现：项目库、标签页、上下文对话、Pi 执行、文件成果、状态同步、有限子代理与一次受控自我升级。

后续实现：全面动态页面、长期机会监控、多平台自动发布、复杂代理群组与运行内核自动优化。

## 16 下一步待验证问题

| 问题 | 验证方法 |
| --- | --- |
| SDK 还是 RPC | 比较事件、控制、隔离与恢复能力 |
| 使用哪些模型 | 用真实任务比较质量、费用与接口兼容性 |
| 选择哪个子代理包 | 固定版本，验证事件、委派、取消、工具权限和 Windows 支持 |
| 状态存储方案 | 验证任务恢复、资产引用和并发一致性 |
| 部署形态 | 明确本地运行、远程后台和多设备需求 |
| 动态页面范围 | 明确组件组合与新增代码开发的边界 |
| 首个业务项目 | 选一个既有实际价值又能覆盖核心链路的任务 |

## 18 开发 Agent 执行要求

开始任务前阅读本文与仓库中的适用指引，核实依赖接口和运行状态。任务需明确目标、范围、验收与预期产物。

实现尽量采用官方扩展接口，避免无必要地修改 Pi 内核。必要的内核变更需独立记录理由、维护成本与恢复方式。

界面操作和 Agent 工具共享业务操作入口；不得用虚构进度或模拟成功替代真实执行。新增工具、技能和发布权限分别管理。

每次交付说明改了什么、如何验证、产物在哪里、哪些仍未验证。新的正式决策及时更新本文，保持它作为主开发依据的连续性。

## 19 产品成功标准

系统是否成功，主要看想法是否更快得到验证，项目是否能持续推进，成果是否可信，切换方向能否恢复，能力是否复用，作品是否值得用户署名，以及用户是否更容易决定下一步。

工具数量、代理数量和自我修改次数仅是运行指标，不能代替实际工作价值。
