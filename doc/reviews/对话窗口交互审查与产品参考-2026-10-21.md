# 对话窗口交互审查与产品参考

日期：2026-10-21。范围：工作台 Pi 对话窗口的信息组织、消息、输入、过程、历史和恢复。当前任务为查询与梳理，本报告不代表已实施改版。

当前的主要问题是对话操作链路没有形成完整产品：消息、运行状态、工具、额度和恢复分别按实现模块堆放，用户需要理解内部结构才能操作。原生能力的保留和工程回归通过，不能据此判定对话体验已经补齐。

## 审查依据

本地在真实 Chrome 中使用当前 `dist` 和独立临时数据进行离线场景复现。日常服务健康检查为 ready，入口引用 `/assets/index-BGjaYl4H.js`，与被检查的 `dist` 一致；没有更改日常项目、账号、会话、配置或布局，没有模型调用，没有重启服务。

证据：[场景记录](../../output/dev-evidence/chat-ui-audit-2026-10-21/report.json)、[复现脚本](../../output/dev-evidence/chat-ui-audit-2026-10-21/probe.ts)。状态和回复由离线夹具生成，证据用于判断真实前端的呈现和操作，不用于评价真实模型效果。

外部对照使用官方产品文档与 Hermes 官方开源代码；没有登录 ChatGPT、Claude 或安装 Hermes 做账户内实操。没有由官方资料确认的精确位置、像素或行为不作为已验证事实。Hermes 暂按 Nous Research 的 Hermes Agent / Hermes Desktop 理解；Dashboard 的嵌入终端和 Desktop 的原生聊天界面是不同参考对象。

另外，加载更早消息没有显式的滚动锚点保持；Ctrl+Enter 处理没有组合输入守卫；每次全局 cursor 更新都会让所有聊天重新读取历史和话题列表。这些是待定向验证的风险，不计作本轮已复现故障。

### 最严重问题的复现

1. 当前对话启动一次执行，并出现待答确认题。
2. 保持该题未答，在同一窗口依次提交三条“排队追问”。
3. 底部只剩三张“排队中”卡；原确认题不在 DOM 中，当前执行的停止入口也不在卡区。
4. 服务端当前执行仍为 `waiting_interaction`。输入区还显示“指导当前执行”，与下方只见排队状态相互矛盾。

这不是折叠太深，而是活动操作被列表截断移除了。不能要求用户通过旧版或取消其他任务绕行，作为当前窗口可用的验收结果。

| --- | --- | --- |

## 窗口如何分区

在现有三层工作台中，对话窗口仍可停靠、浮动和切换项目。下述分区描述窗口内部，不要求给每个聊天窗口复制一套全局侧栏，也不修改底层画板、中层透明布局、顶层不透明浮窗的规则。

```text
工作台全局：空间、当前项目、添加窗口、布局
┌───────────────── 对话窗口 ──────────────────┐
│ 话题名称 / 切换     当前状态       搜索 / 更多 │
├─────────────────────────────────────────────┤
│ 用户消息                                    │
│ 本轮助手活动摘要 → 按需展开工具详情          │
│ 助手回答 / 引用 / 文件结果卡                 │
│ 本条操作：复制、引用、分支等                 │
│                                             │
│ 主消息区：一个主要纵向滚动面                │
├─────────────────────────────────────────────┤
│ 活动状态 / 待答提示 / 排队消息摘要（有才出现）│
│ 待发送附件预览与上传状态                    │
│ 多行输入                                    │
│ ＋ 附件   模型 · 思考 · 时长       发送 / 停止│
└─────────────────────────────────────────────┘
                    按需打开：成果预览或运行详情
```

| 位置 | 放什么 | 展示时机与边界 |
| --- | --- | --- |
| 工作台全局导航 | 空间、项目、窗口、布局、全局设置 | 保留现有机制，不混入单条消息的操作。 |
| 对话标题栏 | 可识别的话题名称、话题切换、新话题、搜索、话题菜单 | 简短而稳定；不长期陈列 token、超时参数和插件清单。 |
| 主消息流 | 用户消息、本轮活动、回答、引用、附件、结果 | 按轮次关联，用户不必自行匹配两个列表。 |
| 活动摘要 | 正在读哪个文件、运行哪个命令、完成了几项、正在重试或等待什么 | 默认为一句可理解的摘要；原始参数、输出和来源按需展开。 |
| 输入框上方状态带 | 当前活动、待答数、已排队消息数、回到最新 | 只占必要高度；待答操作绝不能被“最近三项”裁掉。 |
| 输入区 | 本次输入、待发附件、下一次提交采用的模型和档位、提交动作 | 直接影响这次发送的选项留在附近；标明“下次使用”。 |
| 结果预览 | 文档、图片、代码、命令完整输出 | 宽窗可并排，窄窗切页或全窗打开；支持返回原消息。 |
| 运行详情 | 完整工具、请求账本、费用、插件来源、恢复核对 | 有明确名称与入口，避免全部嵌入“模型请求”。 |
| 话题菜单 | 改名、导出、导入、压缩、查看历史结构 | 低频管理可收纳，但不要依赖滚到历史顶部。 |

默认新对话应优先进入主工作区域。保留手动布局时不能静默移动已有窗口；可以提供“放大对话 / 聚焦当前窗口”及可撤销的默认放置策略。窄窗应减少辅助内容，而不是继续缩小文字。

## 输入框需要参考到什么程度

### 输入和附件

- 输入区从简短输入自然增长，达到建议上限后内部滚动；长文本可展开编辑，不挤掉全部消息。
- 发送与换行规则明确且可配置；继续支持现有 Ctrl+Enter。中文组合输入、候选词确认、快捷键和换行需分别测试。
- 图片与文件的选择、粘贴、拖入是不同入口，都应给即时反馈；不支持的文件明确说明，不应看起来添加成功。
- 待发送附件展示缩略图或格式图标、名称、大小、上传中 / 失败 / 可重试状态；支持预览和移除。
- 上传与提交区分开：上传成功不代表消息已发出，发送失败也不应丢失文字和附件。
- 多窗口、项目切换、刷新后的草稿和附件继续使用现有保存与归属机制。

### 控件怎么放

输入框内部用于写内容；下沿左侧用于附件和能力入口，中部或附近显示本次可用模型、思考档位与普通 / 长任务模式，右侧保留主要提交动作。罕用的无响应秒数、等待秒数、输出 token 上限和完整凭据配置放进明确的 Agent 设置。

模型和思考能力受提供商及当前模型支持情况约束。没有能力时不能画出可用开关；旧任务的冻结配置应在该轮详情中说明。

### 运行状态如何改变输入区

| 状态 | 用户看到什么 | 可以做什么 |
| --- | --- | --- |
| 空闲且无输入 | 简短提示、附件入口、下一次使用的模型 | 输入、添加上下文；发送不可用但原因清楚。 |
| 空闲且有输入 | 明确的发送动作 | 发送、修改、移除附件。 |
| 正在运行 | 一条活动摘要，停止入口稳定可见 | 继续写；明确选择“指导当前执行”或“排队发送”，并显示当前选择。 |
| 等待答复 | 待答题和定位入口，标明来源与期限 | 回答、取消该问题、停止任务；不能把自由输入误当作回答。 |
| 有排队消息 | 排队数量、简短内容和归属 | 查看与取消排队项；编辑或重排属于后续能力，须配套后端支持。 |
| 提交结果未确认 | 保留原提交内容，解释正在核对哪条消息 | 使用同一命令重试；后续编辑的内容不能被旧回执清空。 |
| 正在停止 | “正在停止”，提示可能仍有工具收尾 | 避免重复提交取消；清理未确认时给核对路径。 |
| 失败或中断 | 失败落在相应轮次，给最直接下一步 | 普通重试、核对后恢复、追加额度分别呈现，不混成一个入口。 |

Hermes 的 [运行中提交状态实现](https://github.com/NousResearch/hermes-agent/blob/main/apps/desktop/src/app/chat/composer/busy-submit-state.ts) 把指导、排队、停止作为显式动作，并考虑附件与阻塞问题。适合借鉴这种状态建模；是否采用它的默认动作，需要结合我们已有 Pi steering 与任务排队语义决定。

## 消息需要参考到什么程度

### 消息的内容类型和层级

| 内容 | 呈现建议 |
| --- | --- |
| 用户文字 | 一眼识别为用户输入，保留换行、引用和附件关系；长输入可折叠展开。 |
| 助手回答 | 以可阅读正文为主，宽窗控制行宽，窄窗自然换行；角色与时间作为辅助信息。 |
| 进度说明 | 与本轮回答关联，显示当前进展，避免每次内部事件都生成一条噪声消息。 |
| 工具调用 | 展示动作、对象、状态、必要耗时；展开看参数、来源、完整结果。完成后可收为本轮过程摘要。 |
| 代码和命令 | 保留缩进和内容，带复制、语言或命令标识；横向溢出留在代码块内，避免整个窗口变宽。 |
| 表格和长结果 | 有可阅读的溢出处理，全文可在窗口内或明确的预览面板打开。 |
| 图片和文件 | 缩略图 / 文件卡，打开预览、下载原件，失效时显示真实状态。 |
| 引用 | 来源贴近相应结论，能回到原资料，避免引用路径和技术 ID 铺满正文。 |
| 确认和问答 | 属于当前运行的明确交互卡，有待答、已发送、已送达、超时状态；有专门的定位入口。 |
| 错误 | 放在出错轮次或出错控件附近，说明哪些内容保留、下一步可做什么。 |
| 压缩和系统状态 | 简短事件与详情入口，默认不把摘要元信息当普通助手回答。 |

### 每条消息的操作

先补低风险且高频的复制、选择 / 引用、打开附件、定位所属执行。分支入口应靠近目标消息，默认使用该消息作为分支点；高级树视图留给复杂历史检查。

用户编辑重发、助手重新生成需要保留原版本和分支归属，不能直接改正文或把重试同一任务等同于重新生成。赞踩、分享、语音等并非本次必须实现的功能，仅作为参考产品的其他能力观察。

当前分支操作会“创建并执行”，而不只是生成一个空分支。若未来改成先建分支再输入，需明确调整服务接口和计费触发点，不能只改按钮文案。

### 滚动和连续阅读

- 用户停在底部时，流式输出应自然跟随；主动向上阅读后停止跟随，保留位置。
- 新内容到达但用户正在读旧文时，给“有新消息 / 回到最新”；点击后再恢复跟随。
- 加载更早消息保持当前位置，不能把读者推到新插入内容的顶部。
- 图片加载、代码展开、工具折叠和窗口缩放都应保持阅读锚点。
- 打开已有话题时，应区分“回到上次阅读位置”和“定位正在运行或待答事项”。
- 待答题即使在较早轮次也必须可找回。Hermes 的 [跳转按钮实现](https://github.com/NousResearch/hermes-agent/blob/main/apps/desktop/src/app/chat/scroll-to-bottom-button.tsx) 在待审批时会改为定位该会话的审批区域，而不是盲目滚到最底部。

| 话题导航 | 使用可辨名称、最近活动和简短预览；支持查找、改名、新建与切换；保留窗口与话题的区别。 |
| 初次使用 | 从“选项目→开始聊天”形成直接路径；模型未连接时给可用设置入口，不依赖用户寻找旧版。 |
| 历史分支 | 从本条消息进入，保留来源并可返回；技术节点树不承担普通用户的唯一入口。 |
| 成果阅读 | 聊天与成果并排或切换，修改目标可被选中；把生成、预览、下载、继续修改连起来。 |
| 工具和插件 | 日常只显示当前动作和需处理事项；配置、来源、传输诊断在专门详情中。 |
| 额度与费用 | 提交前知道限制，接近上限有提示；耗尽时解释已用、剩余和继续成本；不能把失败统一归因于额度。 |
| 恢复 | 明确是恢复原任务、另起任务、接续历史还是重试网络提交；使用用户能理解的名称。 |
| 多窗口和项目 | 状态、输入、待答、排队、模型和成果都能看出归属；窗口关闭不等于任务停止。 |
| 键盘和焦点 | 完整 Tab 顺序、明确焦点、菜单退出恢复、中文输入；不能只验证按一次 Tab 后有元素获得焦点。 |
| 窄窗与缩放 | 按窗口宽度而非只按浏览器宽度响应；能聚焦放大，操作不被画板手势截走。 |
| 连接与加载 | 列表和历史有加载状态；重连不重复创建消息，失败不显示假空白，显示最后已知状态。 |
| 文字与图标 | 操作用“读文件、看结果、继续任务”等目的表达；完整 ID、原始 JSON 和技术字段放进诊断详情。 |

## 修复顺序与验收方式

第一步先保证可操作：活动 Run、待答题和停止入口永不因排队或列表截断消失；补全执行历史入口；普通重试和需要核对的恢复可从失败处进入。

第二步处理主阅读和输入：默认主区域、单一主要消息滚动面、跟随 / 回到最新、输入框状态与附件预览。取消用整体缩放掩盖拥挤的做法，但不能在未检查画板坐标换算前直接删除全局 zoom。

第三步整合信息：按轮次呈现回答和过程，设置靠近提交，工具、额度与恢复用各自名字，补齐话题识别与消息操作，成果按需预览。

验收应包含完整连续流程，而不只是逐项控件可点击：

1. 新用户打开工作台，在正常主区域发出第一条消息。
2. 长回复生成时自动跟随；向上阅读不被拉回；能回到最新。
3. 原生工具执行时不打开费用面板也能知道当前动作。
4. 同时有一项待答、三条追问时，仍能答题、停止原执行并区分排队项。
5. 第四次、第五次执行后，早先失败和工具结果仍能直接找回。
6. 发送失败、上传失败、取消和中断后，保留正确的文字、附件与恢复入口。
7. 普通失败无需新增额度即可重试；额度不足时才进入明确的追加路径。
8. 两个同项目话题、两个不同项目话题同时打开，名称、进度、输入与结果不串。
9. 800×600、窄停靠窗、150% 浏览器缩放及中文输入法下，关键操作可见且可达。
10. 相同场景同时覆盖键盘和鼠标，检查真实点击区域与滚动，不以脚本自动滚入视口代替可发现性。

之前 `pi-sweep-ui-qa.ts` 的键盘断言只要求 Tab 后存在非空的焦点信息，部分步骤通过 `scrollIntoViewIfNeeded` 定位目标。它们仍是有用的工程测试，但不能代替上述真实使用验收。

## 与此前测试建议的核对

“在设置选模型和思考”实际要进名为外观设置的弹窗；“查看工具过程”实际要先进模型请求；“压缩上下文”也藏在该面板里；“恢复”需要再展开任务总额度；“从历史分支”位于消息历史顶部，而不是任意消息旁。此前的体验说明没有交代这些真实路径，也没有指出活动操作会被截掉的问题，应予纠正。

本轮交付是问题审查和设计参考。Pi 运行时能力的既有证据继续保留，对话窗口的整体交互体验不能据此写为完成。
