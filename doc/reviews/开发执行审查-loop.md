# 开发执行文档审查：循环、依赖与恢复

日期：2026 年 10 月 5 日
审查对象：[开发执行文档 v0.1](开发执行文档-v0.1.md)、主开发文档 v0.3（旧文档已移除，参见 Git 历史）
范围：只读文档审查，没有运行工程测试，没有授权产品开发。

总体判断：开发循环、证据与授权原则基本完整，问题主要集中在失败分支、离线依赖、阶段验收和任务重启的可操作性。以下 P1 表示开始对应开发前应补齐的流程缺口，并非已运行软件的缺陷。

## P1-01 失败后 continue 可能使 doing 任务丢失或循环重复选任务

章节：第 2、4、8 节。

证据：台账定义 doing、verifying、blocked 等状态，但没有规定验证失败后的状态和任务锁。伪代码在失败后直接 continue，下一轮又选择“依赖就绪的最小任务”，无法确定继续修复当前任务还是改选新任务，也没有失败尝试的持久标识。

影响：不同开发 Agent 可能留下多个 doing 任务，重复选任务或跳过失败任务；中断后无法判定三次尝试已使用多少次。

修改建议：为执行台账定义转移规则。verifying 失败回 doing 并保留唯一主任务；独立阻塞才转 blocked 并释放主任务。修复轮记录 failureId、原因假设、attempt、修复依据与结论。Continue 优先恢复已有 doing，只有该任务结束、阻塞或明确拆分时才选择新的 ready 任务。三次尝试按同一失败原因跨会话累计，证据推翻原因后可新建诊断。

## P1-02 M0-01 真实验证与离线工作的依赖表达不一致

章节：第 3.5、6 节。

证据：文档允许缺凭据时推进离线契约，但 M0-01 同时要求 SDK 会话、事件、取消、恢复；下游依赖 M0-01 接口结论。没有标出哪部分只需固定版本类型/源码，哪部分必须真实模型调用。

影响：可能完全阻断离线开发，也可能把 M0-01 的部分结论当成全部依赖就绪，错误标记实际执行通过。

修改建议：拆为 M0-01a 环境与静态接口探针、M0-01b 真实会话与生命周期验证。M0-02 和基础 UI 可依赖 01a；真实 worker 验收依赖 01b。明确“任务局部证据已通过”与整体 done 的区别；真实验收未通过时 M0 不可完成。

## P1-03 阶段端到端验收失败没有回流机制

章节：第 4、6、7、10 节。

证据：任务全部完成后执行里程碑验收，但伪代码未处理验收失败、责任任务定位及台账更新。

影响：所有任务显示 done，阶段失败却没有 ready 任务，循环可能误报全部阻塞或进入下一里程碑。

修改建议：阶段验收失败创建或重开一个带证据的缺陷任务，关联受影响原任务；里程碑保持未通过。根据根因失效受影响证据，独立通过的任务不全部重开。缺陷修复后重跑失败场景及受影响回归；M0 通过前禁止进入 M1。

## P1-04 干净环境恢复、权限边界、资源清理缺少具体队列归属

章节：第 6 节；对照主文档第 20.6、20.8、20.9 节。

证据：执行队列只在 M0-07 汇总恢复；主文档要求项目授权、跨项目拒绝、执行隔离测试、进程与端口登记，以及干净环境备份恢复。队列 M0-03 未明确权限检查与资源归属，M0-04 未明确备份/导出包，M0-07 没有恢复包前置依赖。

影响：M0-07 才发现没有可恢复包或执行边界，验收阶段变成大量新开发；“执行真实 Pi”可能先于必要边界验证。

修改建议：把执行权限、受限工具白名单、路径/数据外发边界与资源登记归入 M0-03 的启用前置；备份与恢复清单归入 M0-04 或独立任务。无需在 M0 实现未知代码完整沙箱，但明确未验证隔离时只能使用可信固定输入和工具。M0-07 只负责集成与故障验证，并按阶段标出 20.9 哪些场景是 M0、M1 或后续发布验收。

## P2-01 恢复现场时后台进程的事实身份不够明确

章节：第 3、10、11 节。

证据：要求检查后台进程、端口和资源，但 current 只写“运行进程”，没有实例标识、启动时间、工作目录与所有者。

影响：进程 ID 或端口被其他程序复用，接手 Agent 可能误连、误停服务；它也可能清理其他 Agent 的资源。

修改建议：记录 PID、启动时间、cwd、命令摘要、服务实例标识、健康检查地址与所有者；执行清理前核对身份，未知归属资源只诊断不强停。停止开发时列明哪些任务停止、哪些获准继续、如何清理和恢复。

## P2-02 done 与旧证据失效的规则需要一致

章节：第 2、7 节。

证据：done 要求当前代码通过证据，重要改动后旧证据失效，但未规定何时重开原任务，未规定“重要”如何判断。

影响：共享接口或依赖改变后，旧任务仍为 done，最终交付夸大验证覆盖。

修改建议：以受影响模块、契约、依赖和测试覆盖判断失效范围；保留历史通过事实，并另记录当前验证有效性。需要行为修复时重开任务；仅需重验时创建验证任务，避免把全部历史任务重置。阶段门槛只采用当前基线有效证据。

## P2-03 首个实际项目验收没有进入开发队列

章节：第 6、7、10 节；对照主文档第 20.1、20.9 节。

证据：主文档要求固定样例工程验收与实际开源项目使用验收分别保留证据，执行队列偏重固定真实模型产物，没有具体的使用验收任务和输入选择规则。

影响：M0 可以工程通过，但“开源链接到验证结论和稿件”的实际价值仍未验证。

修改建议：阶段结束增加使用验收任务，记录目标到首个成果时间、人工介入、用户反馈；真实项目未选定时标明用户价值验收待办，继续独立工作。隔离不足时真实项目仅资料研究，不能用固定样例运行替代未知项目运行验收。

## 建议整合顺序

先补充台账转移、失败任务回流和阶段失败分支，再拆分离线/真实接口依赖，补齐队列中的执行边界和恢复包，最后完善现场身份、证据失效和真实使用验收。

现有“本次仅写文档、不启动产品开发”的授权边界清楚，应保持。之后开发授权来自用户当前指令；是否需要收费模型或外部发布，应结合既有授权范围判断，不把普通可逆动作自动升级成确认步骤。
