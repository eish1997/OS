# 全能画布开源项目调研与复用建议

日期：2026 年 10 月 15 日  
状态：已确定 OpenPencil 为底座，运行与扩展验证待完成  
对应需求：[OS 全能画布需求文档](全能画布需求文档.md)

## 1 结论

采用复用优先的开发方式：有适合的库就直接接入，有适合的模块就保留来源后移植，仅开发需求缺口和连接部分。

用户已确定 **OpenPencil 为主底座**，优先保留完整编辑体系，再扩展白板、交互节点及 OS 能力。AssetCutter 已有 infinite-canvas 代码作为节点能力来源；Drawnix／Plait、React Flow 等降为局部参考，不作为并行主底座。

选型强调实际使用质量、功能完整性和改造成本。用户反馈 Plait 相关使用体验存在问题，本轮未复现具体缺陷；OpenPencil 的选择也不代表已经完成运行验收。

目前已读取官方仓库、许可证、部分包清单和源码，并检查 AssetCutter 中已有的代码快照。尚未安装运行这些候选，也未完成性能、兼容性和混合交互验收。以下集成成本与优先级是基于所见结构的工程判断。

## 3 优先复用的位置

### 3.1 Drawnix 与 Plait

Drawnix 的 `packages/drawnix`、`packages/react-board` 和 `packages/react-text` 分开提供白板应用、React 视图与文本能力。Plait 核心提供画布、数据操作和插件机制。[Drawnix 结构](https://github.com/plait-board/drawnix#仓储结构)、[Plait 框架](https://github.com/worktile/plait)

已检查 `drawnix.tsx`：存在值、视口、选择变更等回调，并组合绘图、思维导图与手绘插件。适合首先验证嵌入式白板与外部保存接口。其现成 React 组件的扩展入口是否足够，需要实测；必要时在 Plait 层扩展或维护小范围 fork。[源码](https://raw.githubusercontent.com/plait-board/drawnix/develop/packages/drawnix/src/drawnix.tsx)

优先复用：工具栏、选择与编辑交互、白板图形、思维导图和画笔。不能将框架插件机制直接等同于我们要求的“agent 安全开发、测试和发布任意节点”。

### 3.2 OpenPencil

该项目提供本地设计编辑、组件与布局、CLI／MCP 及 agent 接入，技术栈包括 Vue、CanvasKit 和 Tauri。适合我们的设计与可编程画布方向，但不是现有 React 界面可直接替换的组件。[官方仓库](https://github.com/open-pencil/open-pencil)

包结构已分出 `scene-graph`、`core`、`vue`、`fig`、`cli`、`mcp` 等。优先研究场景对象、编辑操作与自动化接口的复用，判断是否能保留现有 UI 技术，或以独立编辑器模块承载。[包清单](https://raw.githubusercontent.com/open-pencil/open-pencil/master/package.json)、[核心包](https://raw.githubusercontent.com/open-pencil/open-pencil/master/packages/core/package.json)

必须验证：我们定义的交互节点能否自然进入同一画布，白板连线与设计图层如何共存，以及保存与撤销是否统一。支持 agent 编辑设计不等于已具备任意节点代码的开发、隔离运行和发布体系。

### 3.3 AssetCutter 已有的 infinite-canvas 代码

本地 `F:/AI/assetcutter-ai-pro/vendor/basketikun-infinite-canvas/SOURCE.txt` 记录了来源：

- 上游：`basketikun/infinite-canvas`。
- 标签：`v0.19.0`。
- 提交：`e856c878e0a34651bb828e28f0af20d71016a7d4`。
- 快照保留了 LICENSE 和 NOTICE。

已检查本地快照中的具体复用位置：

| 路径 | 可复用内容 | 需要调整 |
| --- | --- | --- |
| `types/canvas-plugin.ts` | 节点定义、尺寸、配置、宿主能力、AI 调用接口 | 对接 OS 的素材和任务模型，补版本与权限协议 |
| `lib/canvas/node-registry.ts` | 注册与注销节点、默认规格、插件归属 | 补重名处理、版本锁定和缺失扩展恢复 |
| `lib/canvas/plugin-loader.ts` | 下载、安装、启停、更新、清理和本地开发加载 | 改造执行隔离、更新策略和故障处理 |
| `lib/canvas/plugin-runtime.ts` | 宿主运行接口、React 与事件能力 | 缩小权限范围，隔离样式和不可信代码 |
| `components/canvas/infinite-canvas.tsx` | 视口和平移等基础交互 | 与白板和设计工具统一交互规则 |

已见的加载器通过 Blob URL 动态导入代码，在主页面运行，并允许向页面注入 CSS。它是可复用的开发基础，但不是隔离沙箱。不能直接用于承载任意生成代码后就宣称满足需求。

上述结论来自本地移植版本，未证明与上游提交逐文件一致。正式复用时必须区分原始代码和 AssetCutter 的修改，保留两部分来源。上游目前也提示历史存储格式可能变化，宜固定版本后由我们管理兼容性。[上游说明](https://github.com/basketikun/infinite-canvas)

### 3.4 React Flow

官方自定义节点可以直接使用 React 组件，适合表单、按钮和交互预览。优先作为执行节点底座的比较对象，而非预先认定为整个全能画布底座。[自定义节点文档](https://reactflow.dev/learn/customization/custom-nodes)

若最终选择它，需要验证白板对象、图层与设计编辑的表达成本。其核心库许可不代表所有 Pro 示例、素材和配套内容都适用同一许可。[核心仓库](https://github.com/xyflow/xyflow)

## 4 其他候选的使用边界

- **Excalidraw**：适合快速获得白板交互，重点评估现有编辑器 API 与我们任意交互节点的兼容成本。[官方项目](https://github.com/excalidraw/excalidraw)
- **LeaferJS**：适合更深的渲染定制，但需要自行补产品层。仓库性能宣传不作为本机混合内容基准。[官方项目](https://github.com/leaferjs/leafer-ui)
- **Penpot**：适合学习组件、设计变量及布局流程；若提取实现，需核对具体模块依赖与 MPL 文件边界。[官方项目](https://github.com/penpot/penpot)
- **BlockSuite**：文档和画布共用内容模型与我们的目标相近，但上游维护调整需先澄清，不能仅按旧教程选型。[官方 README](https://raw.githubusercontent.com/toeverything/blocksuite/master/README.md)、[调整公告](https://github.com/toeverything/blocksuite/issues/9045)
- **DGM.js**：脚本化智能形状值得参考；许可与维护方式都应纳入成本。[官方说明](https://github.com/dgmjs/dgmjs)
- **tldraw**：可研究交互和 MIT 示例；SDK 生产使用需要合适授权。个人本机日常使用不能仅凭“本地”二字认定为内部开发环境。[许可说明](https://github.com/tldraw/tldraw/blob/main/apps/docs/content/community/license.mdx)

## 5 网页节点需要单独验证

网页承载不能由某个白板库自动解决。Electron 官方列出 iframe、webview 和 WebContentsView 三种方式，并明确不推荐使用 webview。WebContentsView 不属于 DOM，其定位与尺寸需要主进程和渲染进程协调。[Electron 官方说明](https://www.electronjs.org/docs/latest/tutorial/web-embeds)

据此，候选方案必须验证网页节点随画布平移缩放时的坐标、裁剪、遮挡、输入焦点和暂停行为。不能直接把 WebContentsView 当作普通 React 节点，也不能把 iframe 成功显示一个网站推广为所有网站可用。

桌面承载框架保持待定。独立验证浏览器能力，再决定与所选图形底座的组合方式。

## 6 复用规则

1. 优先直接依赖稳定公开接口；只有需要改底层时才复制模块或维护 fork。
2. 对复制代码记录上游地址、提交、原始文件、许可证和我们的修改，保留所需版权与许可声明。
3. MIT 代码可按许可复用；MPL、GPL 和自定义许可分别处理，不把整个仓库默认当作 MIT。实际引入时继续检查子包、字体、图标及其他资源。
4. 固定版本，管理升级差异；不自动追随会破坏作品格式的主分支。
5. 上游编辑器采用自己的内部模型是正常的；对 OS 暴露明确接口，避免将多个完整编辑器的数据和事件系统直接拼接。
6. 必须统一对象身份、坐标、选区、撤销、保存和生命周期。不能用几个互不连通的画布冒充一个全能画布。

## 7 下一步验证与决策条件

以 OpenPencil 为主线：固定上游提交，在本机跑通原版，记录编辑与保存基线，再验证白板补充、节点隔离、agent 和 OS 接入。优先沿用其 Vue 编辑器，不先为适配 React 重写完整界面。

参考或移植 infinite-canvas 的节点协议与开发流程；具体 UI 与运行方式按 OpenPencil 的承载能力适配。其他项目仅在出现明确缺口时评估，不默认批量引入。

用以下小样本确定扩展边界并保护原版功能：

| 验证项 | 必须观察的结果 |
| --- | --- |
| 混合对象 | 文字、图形、图片和真实滑杆节点能共存，选区与焦点正确 |
| 设计基础 | 画框嵌套、文字编辑、尺寸调整与布局不破坏对象关系 |
| 动态节点 | 加载、更新、停用及恢复节点，保留测试数据 |
| 故障隔离 | 节点异常后画布仍可编辑，agent 可获得错误信息 |
| 统一历史 | 跨对象编辑能撤销重做，重开后布局和引用保持 |
| 浏览器承载 | 网页导航、滚动、遮挡、缩放与画布交互可协调 |
| agent 接口 | 外部指令可创建或更新对象，且纳入同一历史与保存机制 |
| 接入 OS | 核心能独立运行，通过接口接入素材、任务与保存 |

本轮未执行上述运行验证。底座方向已确认，后续需用实际结果确定改造范围与成本；若遇到核心阻碍，先记录证据并讨论，不自行切换底座。无需先开发全套 OS，也无需批量搬入其他候选仓库。
