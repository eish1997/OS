# 自我修改、评价、权限与发布恢复审查

审查范围：主开发文档第 6.6、7、8、9、11、12、14、18 节。主文档只读。本报告是开发规格审查，不代表现有系统已存在漏洞；优先级表示应在对应能力启用前落实。

## 总体判断

文档已经正确提出独立候选、固定验收、稳定底座和恢复，但仍是原则级描述。缺少可执行的权限边界、变更状态机、验证材料、发布一致性和恢复数据策略。最大风险不是 Agent 不会写扩展，而是候选在未被可靠验证时获得执行权限，或代码恢复后数据与已发生的外部行为无法恢复。

## 发现与具体修订

### E1 [P0] 隔离副本没有定义执行权限隔离

位置：6.6、10、11.2 第 3 项、12。

问题：独立目录/分支只能隔离文件版本，不能阻止候选脚本访问主项目目录、凭据、宿主命令或发布控制。尤其开源安装脚本和 Pi 扩展本身就是可执行代码。

修订：定义候选执行环境清单：可读目录、可写目录、允许网络目的地、允许命令/工具、凭据引用、预算、进程清理规则。首版将未知开源代码试运行放在独立容器/虚拟机或等效隔离执行器；普通目录隔离不得标为安全隔离。明确 Windows 下具体技术及不可用时降级为只读分析，不自动试运行。能力 API 的权限在宿主操作网关强制检查，不能仅靠提示词。

验收：候选尝试写入生产资产、读取生产令牌、调用发布操作，均被执行层拒绝并留下记录；终止实验后子进程和端口释放。

### E2 [P0] 授权未绑定具体版本与作用范围

位置：7 “安装功能不等于取得新增权限”、8 Capability、11.2 第 6 项。

问题：“授权范围内启用”缺少可存储、可撤销的授权对象。包升级可能继承原有高权限；子代理委派可能放大权限。

修订：增加 Grant 对象（主体、项目/资产范围、能力版本或构建摘要、动作、有效期、预算、委派许可、撤销状态）。委派权限取父授权与子角色权限交集，不能扩大。扩展更新权限增加时进入待授权；未增加且符合既有策略的更新可继续自主启用，避免所有改动都向用户确认。

验收：旧版本授权不自动覆盖权限扩大的新版；撤销后新操作拒绝；子代理不能委派更高权限。

### E3 [P0] 自我发布缺少版本状态机和原子切换协议

位置：8 Change、11.2、14 阶段四。

问题：没有规定何时算测试通过、何时可启用、失败如何阻止半新半旧环境，也未规定多个改进同时发布的冲突。

修订：Change 状态至少为 proposed → building → validating → validated → activating → active，另含 rejected/failed/rolled_back。记录基础版本、候选不可变构建摘要、依赖锁、测试报告、策略版本、数据模式版本。发布控制持有单一发布锁，检查候选基线仍为当前版本；不同基线先合并重验。激活采用启动新环境、健康检查、切换版本指针、保留旧环境的协议，明确在途任务固定使用原版本。

验收：激活时断电/崩溃，重启后能确定运行旧版或完整新版；两个候选不会覆盖彼此；在途任务不会中途改变工具语义。

### E4 [P0] 恢复只描述代码，未处理数据迁移及外部副作用

位置：11.2 第 3、7 项、11.3、14 阶段四。

问题：“恢复后可启动”不足以证明旧项目还能使用。新插件可能改变数据库和文件格式，代码回退后不兼容；已发布文章和发送的请求无法随版本回退撤销。

修订：每个发布声明数据迁移类型（无迁移/向后兼容/不可逆），记录快照和恢复点。首版自我升级仅允许无迁移或可验证的向后兼容迁移；不可逆迁移走独立流程。备份恢复由稳定底座执行，候选不能覆盖唯一备份。发布记录区分代码恢复、数据恢复、外部补偿；外部操作以幂等标识和结果对账，明确不可撤回状态。

验收：旧版读取升级期间写入的资产成功；恢复不删除无关用户新数据；无法撤回的外部行为清楚标示而非显示“完全恢复”。

### E5 [P1] 保留评价任务没有防污染机制与通过规则

位置：11.2 第 5 项、11.3、11.4、19。

问题：有固定标准原则，但没有说明谁保存保留题、候选可否查看、通过阈值如何确定。开发代理可能针对已知测试优化，也可能牺牲成本、事实质量换取某项评分。

修订：建立 EvaluationSuite，记录测试集版本、适用能力、不可退化项、比较指标、成本上限和通过规则。公开开发样例与受验证器保护的保留任务分开；候选只能收到失败摘要与可公开案例。确定性工具测试与模型评价分别记录，模型评价附模型/提示词/证据及不确定性。对模型随机性允许预定义重复次数与容差，避免一次偶然成功就晋级。

验收：候选无法改写保留标准；提高一项质量但破坏权限、幂等或历史数据的候选被拒绝；评估可按锁定配置复现。

### E6 [P1] 记忆学习可绕过正式变更与被外部内容污染

位置：5.1、5.4、11.1。

问题：记忆可修改，但未区分用户偏好、外部资料、推断和执行策略。网页中的指令可能被沉淀为技能；一次反馈可能被错误推广为永久偏好。

修订：记忆条目记录类型、来源、时间、适用范围、可信状态及更正关系。用户明确偏好可直接保存；Agent 推断先作为暂定；外部内容仅作为资料。权限和发布政策存于独立策略，记忆不能修改。自动提炼技能先进入候选区，并按能力变更流程验证。

验收：网页“忽略权限”等文本不改变工具策略；项目局部偏好不影响全部项目；用户能更正或删除条目，并知道后续何时停止使用。

### E7 [P1] 供应链登记有版本，但没有构建与升级规则

位置：7、12。

问题：固定版本尚不能明确依赖树、安装脚本、来源包与运行包是否相同，以及插件更新后如何停止加载问题版本。

修订：能力包记录源 commit/包摘要、锁文件、许可证、构建步骤、安装生命周期脚本、依赖清单和验证环境。下载、安装、试运行、注册分为不同状态；安装脚本也运行在候选隔离环境。禁止运行时自动追踪 latest；升级作为 Change 重验。提供撤销能力版本和依赖能力影响列表，保留最近可用构建。

验收：篡改构建无法与已验证摘要匹配；依赖升级触发重验；禁用问题能力后排队任务得到明确阻塞原因。

### E8 [P1] 改进触发缺少抑制与反馈闭环

位置：11.2 第 1、2 项、14 阶段六。

问题：重复失败触发改进可能导致系统不断开发自己，消耗资源并频繁改变体验；没有如何判断改进收益持续存在。

修订：每个问题关联改进候选，合并重复原因；设每日改进预算、最大候选次数、冷却周期及停止条件。上线观察窗记录成功率、成本、用户修正率；明确异常阈值与回退行为。主任务预算与系统改进预算分别计账，用户任务优先级更高。首版仅用户明确需求触发系统代码修改，失败自动触发诊断与建议；后续满足策略后再自动开发低风险技能。

验收：同一失败不无限创建候选；预算耗尽后正常工作任务仍可继续；新版本收益消失或回归时可定位并停用。

## 建议主文档新增的最小规格

1. 第 8 节增加 Grant、EvaluationSuite、Release 对象；Change 引用这些对象。
2. 第 11 节补“变更分级与自动启用策略”“候选隔离与构建摘要”“发布状态机”“数据恢复与外部补偿”。
3. 第 12 节补安装脚本隔离、不可变构建、依赖锁定和版本撤销。
4. 阶段一先验证权限网关及隔离可行性；阶段四增加激活中断、权限拒绝、历史数据兼容和恢复后任务正确性的验收，不只检查新功能和启动。

## 范围控制

这些修订不意味着第一版必须实现完整自动内核优化。第一次自我升级可以限定为纯展示型图片对比插件：声明式视图、只读资产接口、无数据迁移、无新增外部凭据。这样仍能验证“对话提出需求 → 生成能力 → 评价 → 启用 → 恢复”的核心闭环，同时将高权限改进留到后续阶段。
