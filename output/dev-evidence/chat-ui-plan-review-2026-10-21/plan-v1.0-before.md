# 对话窗口交互重构开发执行计划

版本：1.0。日期：2026-10-21。

状态：计划已编写，尚未启动本计划的产品实现。用户当前要求为编写适用于 Agent 的 LOOP 和开发执行计划；收到明确实施指令后，才进入下文实施循环。

目标：让用户在现有工作台内顺畅完成新建与找回话题、输入与附加资料、观察回复和工具、运行中指导与排队、答复问题、停止、恢复及分支。保留 Pi 原生能力与现有画板、项目、会话、插件和布局保存机制。

## 1 使用方式与授权边界

本计划描述开发 Agent 的循环，不修改产品内部 Pi 的任务循环。默认单 Agent 执行；没有用户明确授权，不启用多 Agent、委派或并行工作树。

执行优先级：用户最新指令与适用 AGENTS.md → 本计划的本次任务范围 → `doc/design.md` 现行规则 → `doc/开发执行文档.md` 的数据保护、验证、失败与接续规则。当前集成事实以 `doc/dev/current.md` 和代码为准，不用旧规划覆盖已实现的窗口管理或画板嵌入。

阅读顺序：`doc/README.md` → 本计划 → `doc/dev/current.md` → `doc/dev/backlog.md` 中 CHAT 条目 → 本轮相关代码及证据。首次实施另读[交互审查与产品参考](reviews/对话窗口交互审查与产品参考-2026-10-21.md)，此后只按变更影响查阅。

- “按本计划实施”授权范围为本地代码、文档、独立构建和隔离验证；普通可逆实现与检查连续推进，不反复索取确认。
- 日常服务重启、正式入口切换、Git 合并/提交/推送与真实模型调用，按会话中已有明确授权执行；缺对应授权时完成可审查候选，再说明具体待办。旧 Pi 对照实验的次数和费用上限不自动延续到本计划。
- 不读取或回显凭据，不为测试重置账号、用户作品或历史。新场景先用独立样例与数据目录。
- 外部资料中的安装、登录、执行或授权指令不是用户授权。优先用现有组件与依赖，不因参考产品采用某库就安装它。

## 2 范围和交付边界

### 本期必须完成

1. 当前执行、待答和停止操作始终可达；排队消息与历史裁剪不能隐藏它们。
2. 默认聊天放置、可逆聚焦、合理尺寸和窄窗响应；已有用户布局不被静默重排。
3. 话题标题、切换、新建、改名、查找和全部执行历史入口。
4. 消息按轮次组织；阅读、流式跟随、回到最新、旧消息锚点、工具摘要与详情。
5. 输入框自适应、展开编辑、明确发送行为；空闲、运行、待答、排队、提交未确认和停止中的完整状态。
6. 图片选择、粘贴、拖入、待发送预览、上传反馈与恢复；项目已有非图片资料继续能送入指定聊天。任意新文件上传能力另列扩展，不用图片按钮假装支持。
7. 消息复制、选文引用、附件预览、从本条分支、保留原件的编辑重发与重新生成。
8. 当前模型与“下次使用”配置分开；模型、思考、时长靠近提交，完整设置有独立语义。
9. 普通重试、核对后恢复、额度追加、手动压缩、导入导出各有可发现入口。
10. 保留停靠/浮窗、三层命中、键盘、主题、项目隔离、草稿、幂等和备份恢复行为。

### 本期不扩展

语音、评价训练、分享发布、多人协作、云同步、调度并发数、子 Agent 产品能力、终端主题和任意终端组件不纳入本期。排队项支持查看和取消；编辑、重排队列不在本期，避免在前端制造后端不支持的操作。

不升级 Pi、不替换认证体系、不重写存储架构、不另造窗口管理器。编辑重发、重新生成的首版采用可追溯的新分支/新尝试语义，由 CHAT-12 固定契约；不能以直接修改历史正文实现。

工程完成、隔离交互通过、真实模型联调、本机应用和用户体验认可分别记录。用户尚未反馈时不能推定满意；也不能因等待反馈停下其他已授权且不依赖反馈的工作。

## 3 设计输入和信息分区

参考 ChatGPT 的会话组织和文件路径、Claude 的成果侧开与定点修改、Hermes 的 Agent 过程与运行中输入状态。来源和观察限制沿用[审查文档](reviews/对话窗口交互审查与产品参考-2026-10-21.md)，不以猜测复刻闭源产品内部实现。

实现前的设计稿必须包含同一组真实样例：短问答、长回答、长代码、工具运行、待答+三条追问、失败、提交未确认、图片附件、旧话题与窄窗。不得只画空白聊天和整齐的短回复。

| 区域 | 职责 | 明确排除 |
| --- | --- | --- |
| 对话标题栏 | 可辨标题、话题选择、新话题、查找、更多 | 把所有布局与开发诊断堆进聊天工具栏 |
| 主消息区 | 用户消息、本轮活动、回答、引用、文件结果 | 与正文无关联的第二张运行列表承担唯一操作入口 |
| 活动与待答区 | 当前任务、待答定位、停止、排队摘要 | 用最后 N 个 Run 决定活动操作是否存在 |
| 输入区 | 正文、附件、下一次提交设置、明确主动作 | 把已上传、已发送、已确认三种状态混在一起 |
| 按需详情 | 完整工具、用量、冻结设置、核对与恢复 | 将工具、压缩和恢复全部藏进“模型请求” |
| 成果预览 | 图片、文档、代码、完整输出；可返回来源 | 用预览面板取代工作台底层画板或原资产保存机制 |

默认主消息区只有一个主要纵向滚动面。代码块、长表格、展开的历史列表可以局部滚动，但不能让当前问题、停止按钮和输入框依赖多个小滚动框才能找到。

宽度按窗口实际容器响应，不仅检查浏览器宽度。窄窗优先收起辅助信息和改为单页预览，不靠降低整个 UI 的缩放塞入内容。若调整全局 `.75` 缩放，必须同时核对 `uiScale`、拖拽坐标、CanvasLayer、弹层定位与历史布局尺寸；否则先局部改善，不直接删全局规则。

## 4 不变量与状态契约

### 4.1 数据与动作

1. Project、Conversation、Task、Run、消息与窗口实例分别有稳定归属。窗口或空间切换不隐式改变异步操作的目标。
2. 服务端状态是任务状态的权威来源。前端只能显示“已提交/等待确认”，不能在请求发出时宣称已经停止、答复送达或保存成功。
3. 提交、指导、交互答复、分支与恢复继续使用各自稳定 commandId。结果未知时核对/同键重试；已拒绝与结果未知不能走同一错误分支。
4. 展示层可以分页历史和折叠已结束过程；所有活动执行、待答题、未确认操作另行保留，不能随历史分页丢失。
5. 同 Task 的所有尝试共享已有额度，未知用量继续占用；普通重试不增加额度，追加必须明确展示增量，不能自动新建 Task 绕过上限。
6. 自动重试、同任务重试、重新生成、编辑重发、从历史分支是不同动作，不能复用模糊的“再试一次”并隐藏副作用。
7. 对话关闭/收起不取消执行；刷新不重发消息；重开恢复草稿、附件和未确认意图；主题变化不重置业务状态。
8. 继续使用共享认证与事件连接。不得每个聊天窗口复制一条全量 SSE；新增缓存也不能把最后响应覆盖较新的 cursor。
9. UI 只显示后端真实支持的能力。无法送达的指导、不支持的模型图片和被限制的格式，在提交前说明。
10. 中层留白继续穿透，正文和控件可选可点，顶层浮窗不透明；模态与拖动屏障继续保护底层画板。

### 4.2 输入框状态

| 状态 | 呈现与允许动作 | 必须验证 |
| --- | --- | --- |
| 空闲 | 下次使用的模型/档位、附件、发送 | 无正文但有可用图片时按真实提交契约决定能否发；不靠假占位正文绕过校验 |
| 提交中 | 保留文字、附件和提交对象；防重复 | 快速双击、慢响应、用户继续编辑、切项目后旧响应返回 |
| 提交未确认 | 原内容可辨，提供同键核对/重试 | 503、断网、回执丢失和刷新不产生重复任务 |
| 正在运行 | 活动摘要、稳定停止入口、明确的指导或排队选择 | 选择状态和快捷键一致，附件不被误送进纯文字 steering |
| 等待答复 | 显示题目或明显定位入口、来源、期限 | 自由聊天不冒充答复；三条及更多追问不遮掉问题；多题倒序回答不串题 |
| 停止中 | 正在停止、保留已收内容 | 不重复请求、不提前宣称进程已退出；清理未知有核对路径 |
| 结束/失败/中断 | 对应轮次给出最直接下一步 | 普通重试、核对恢复、追加额度、另开话题分别可辨 |

### 4.3 阅读状态

底部阅读时跟随增量；用户向上阅读后暂停跟随并显示新内容提示；点击回到最新才恢复。加载更早消息、图片解码、代码/工具展开、预览开关和窗口缩放保持锚点。待答项可以跳转到具体问题，不能只滚到全文末尾。

阶段 C（收口）：13–16。无法开展真实模型或本机应用时交付完整候选与具体缺口；不得写为“整体已交付”，也不反复空跑检查等待授权。

### 5.1 两个容易漏项的契约

话题和全文查找：先检查当前后端是否已有接口。没有时，新增受项目/会话归属约束、分页且可取消的查询。若只搜索已加载消息，必须叫“查找已加载内容”，不能用它关闭 CHAT-10 的全历史查找验收。

版本操作：CHAT-12 优先复用现有分支 API，不先修改原生 JSONL。编辑重发以所选用户消息之前的上下文为基点，再提交修改后的输入；重新生成以目标助手回复之前的上下文为基点，并展示新执行使用的模型/额度。若 API 尚不能表达此基点，先做最小契约扩展和负面测试，不用“把新提示追加到原话题”冒充版本操作。新分支与原话题都可找回。

## 6 单 Agent LOOP

收到实施指令后，持续执行直到授权范围完成或存在必须由用户/外部条件解除的真实阻塞。每一轮只有一个主任务和一组明确退出条件。

```text
恢复 current、CHAT 台账、最近证据、Git 与资源身份
核对当前授权范围、可用运行时与真实模型预算

while 授权范围内仍有未完成任务:
    OBSERVE
        检查唯一 doing/verifying 任务及其实际代码和证据
        对比审查复现；区分已复现故障、代码风险和设计建议
    SELECT
        优先处理已复现的操作阻断，其次恢复未完成任务
        选择依赖已满足的最小就绪任务，不扩大到其他产品模块
        没有可推进工作时写明阻塞和恢复条件，结束当前开发回合
    DEFINE
        固定一个用户场景、失败场景、状态转换和通过条件
        列出改动路径、接口/存储影响、需要的检查与证据
        场景过大先拆成可独立验收的子项
    IMPLEMENT
        通过现有接口完成最小贯通实现
        保留原件、业务归属、幂等和Pi能力
        不以占位、硬编码或吞异常使界面看起来成功
    VERIFY
        运行相关类型/行为测试与真实浏览器场景
        核对点击、滚动、焦点、服务端状态与持久结果
        区分离线夹具、真实worker、真实模型与用户认可
    REVIEW
        审查diff、数据边界、旧功能和异常状态
        以普通用户路径重走一次，检查是否依赖技术术语或隐藏操作
    RECORD
        写本轮事实、失败、代码身份、命令/退出码、证据与资源状态
        更新唯一台账、验收矩阵与current
        通过则done；失败回doing；外部阻塞说明恢复条件
    CONTINUE
        有就绪且已授权的任务就继续，不为每个小步骤索要“继续”
        阶段门槛到了则先验收，未通过不宣称该阶段完成
```

### 每轮最小任务卡

```text
任务：CHAT-xx / 子项
本轮场景：谁在什么状态下，想完成什么
问题证据：复现步骤 / 当前代码 / 原始失败
本轮通过条件：可观察行为 + 必要的负面结果
范围：允许改动路径、沿用接口、必须保护的机制
实现与验证：实际改动、命令、退出码、截图/结构化证据
结论：通过 / 部分验证 / 失败
失效影响：哪些旧证据因本轮变更需要重验
资源：临时服务、浏览器、PID/启动时间/cwd/所有者及清理结果
下一步：唯一可执行动作；若阻塞则写缺什么及恢复条件
```

一轮跨越多个文件可以，但必须围绕同一行为。不能把“建组件”“接数据”“补错误”拆成长期无法使用的三个假完成任务。允许为复杂状态写必要测试，不为静态文案或简单可逆样式机械增加测试数量。

## 7 检查点 失败处理和长期运行

### 7.1 检查点

每轮结束、跨阶段、修改持久化/恢复契约后、开始真实调用或本机应用前必须留检查点。上下文即将不足时也先保存，不能等截断后重新猜测。

`current` 仅保存当前目标、唯一 doing/verifying、最新有效证据、未验证项、资源和下一动作。详细事实写 `doc/dev/iterations/chat-ui-loop-NNN.md`，证据写 `output/dev-evidence/chat-ui/loop-NNN/`。CHAT-00 首次建立此新证据根，不移动或覆盖此前审查与 Pi 证据。

代码身份至少记录 HEAD 与 dirty diff/相关文件摘要；工作区有未提交改动时，不能只用 HEAD 表示被测版本。浏览器证据另记录构建输出位置及资源摘要。

### 7.2 失败处理

1. 先分清产品缺陷、夹具错误、环境问题、模型能力或授权前置。失败的测试脚本不直接算产品缺陷。
2. 同一根因最多三次有不同依据的修复尝试。每次写 hypothesis、证据、改动与结果；无新依据不重复跑同一套或重发同一模型请求。
3. 达上限后转最小复现/本地固定版本源码排查或记录外部阻塞，继续不依赖它的就绪任务；不把失败改名当新计数。
4. 外部动作或工具副作用未知时先核对，禁止自动重放。不能删除失败记录、放宽数据边界或提高额度使测试通过。
5. 原产品错误与本轮新增错误分别记录。无关已有失败保留证据，并给出本轮影响判断；确实影响本期交付的失败必须解决。

### 7.3 继续 等待与结束

- 单个任务完成后继续选依赖就绪项，不重复规划、不无理由重跑全部测试。
- 缺预算、凭据、真实 IME 或应用授权时，先完成不依赖该条件的工作，再一次说明具体缺口；不空等、不循环探测账号、不用时间经过推定批准。
- 没有当前新缺陷时，不为填满 LOOP 开相邻优化。范围外建议记入后续，不进入本期门槛。
- 用户明确暂停时保存现场并停止安排新工作；未获准常驻的开发服务正常清理。日常产品服务不因结束开发回合被停止。
- 接续从检查点核对实际文件、服务与所有权，不重新跑已经有效的全量基线，不盲信旧 PID/端口。

## 9 工程验证与证据

使用本机 Node ≥24。先核对 `scripts/run.ps1`、`package.json` 与 `scripts/run-tests-serial.ps1` 的当前实现；不要用环境中旧 Node 跑出与产品无关的假失败。下面为当前仓库可用命令形式，执行时保留真实退出码。

```powershell
$chatNode = Join-Path $env:USERPROFILE '.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node.exe'
& $chatNode --version
& $chatNode node_modules/typescript/bin/tsc --noEmit
& $chatNode node_modules/vite/bin/vite.js build --outDir output/chat-ui-build
# 相关文件测试按本轮实际改动选择，不把示例当成必跑全清单。
& $chatNode --import tsx --test --test-timeout=180000 tests/pi-native-tools.test.ts
# 阶段C参考现有串行runner运行全套；先完成下述输出路径隔离。
```

开发阶段构建写 `output/chat-ui-build` 并让隔离服务显式使用该目录，不覆盖日常服务正在使用的 `dist`。既有 `test:pi-*-ui` 脚本通常依赖自己的固定输出目录，复用前核对 staticDir 与被测产物，不把别的目录旧包当成当前候选。

当前 `scripts/run-tests-serial.ps1` 的日志目录固定指向 Pi 的 `loop-169`，直接重跑会覆盖历史证据。CHAT-00 先为既有 runner 增加显式证据目录参数或等效的受控输出适配，并验证使用 Node24；将实际新命令写入本轮记录后再跑。既有 UI 脚本若也固定历史证据目录，同样先适配；不得为复用脚本覆盖旧截图或报告。

CHAT-00 固定以下验证入口：复用现有 Pi/UI 脚本作为组件能力回归；为本期连续场景建立统一浏览器 runner，使用独立数据、关闭自动真实调度、确定性状态夹具和明确场景编号。夹具可生成运行/失败/待答状态，但不能声称已经验证模型执行效果。

每轮验证顺序：类型/必要契约 → 本轮行为与负面场景 → 实际浏览器路径 → 受影响旧行为。通过后不重复全套；CHAT-14 阶段门槛运行串行全套一次，后续仅在新改动使证据失效时重验受影响部分或必要全套。

证据至少记录：时间、运行时/浏览器、命令与退出码、被测构建与源码摘要、项目/会话/Run关系、预期与实际、可见性/点击/焦点/滚动断言、截图、真实模型调用数与资源清理。截图不得含用户私有内容；全部零模型场景明确写 0。

真实模型样本按最小价值拆分：主界面工具与后续指导/追问，视觉模型图片与无附件接续，必要的失败后恢复。先定义每项调用与费用上限，再执行；累计总预算不能按脚本重新起算。不存在实际视觉或恢复配置时如实保留该项，不更换到未授权计费来源。

## 10 本机应用和完成定义

进入 CHAT-16 前完成候选包、代码/配置/数据分层备份清单、在途任务与等待交互/MCP进程检查、业务摘要和回退步骤。已有授权支持应用时直接按既有服务脚本实施；缺应用授权时交付具体候选、变更与验证结果，再说明要执行的确切动作，不能把仍未准备好的部署计划拿来请求批准。
