# Pi 能力保留与体验补齐开发计划

版本：1.1  
日期：2026-10-16  
状态：开发计划；实际进度以 `dev/backlog.md` 为准，本文件不代表已交付，也不扩大当前会话的实施授权。  
依据：[Pi底座完整性联合复查](reviews/pi-capability-audit-2026-10-16.md)。

## 阅读指引：这份计划解决什么

对用户来说，关键问题是：原版 Pi 能完成的开发任务，放进我们的工作台后，是否仍能完成，遇到中断是否能继续，操作是否看得懂。这不能仅凭“底层用了 Pi”判断，需要把原版能力逐项对应到工作台，并用实际任务验证。

本计划按以下顺序交付，每一阶段都要有从页面到实际执行的证据：

1. **先保证能持续工作。** 核清底座能力，补齐模型设置、用量记录、上下文压缩、大历史接续和长任务恢复。
2. **再保证用户看得见、能纠正。** 展示实时回复和工具进度，区分中途指导、排队追问与停止。
3. **补齐扩展与日常操作。** 接入 MCP 等原版扩展能力，让插件能在网页询问用户，并支持图片和历史分支。
4. **最后证明没有明显退化并交付。** 用固定版本原版 Pi 做同条件任务对照，检查旧数据、实际入口、使用说明和回退方案。

第4节是开发任务，第6节是验收清单，第8节规定 Agent 长时间工作的循环与断点接续，第9节规定何时才能宣布交付。实施进度查看 [唯一任务台账](dev/backlog.md)，能力差异查看 [能力清单](dev/pi-capabilities.md)。本计划中的“必须达到”均为要求，不表示功能已经完成。

## 1. 目标与执行边界

### 给项目负责人的阶段检查点

不需要阅读代码也可以按以下结果判断进度。开发 Agent 每阶段应提供可操作入口、演示步骤、验证证据和未完成项；只提交代码或报告测试数量不能替代阶段验收。

| 检查点 | 你应该能实际做什么 | 不能据此推断什么 |
| --- | --- | --- |
| A：能持续工作 | 选择模型与思考档位，看到剩余额度；长对话能够压缩，任务到期或中断后有明确恢复入口 | 不等于所有插件、图片和中途纠正已支持 |
| B：看得见、能纠正 | 执行时看到回复和工具进度，刷新后记录仍在；分别使用中途指导、排队追问和停止 | 不承诺立即打断正在执行的系统命令 |
| C：日常能力接齐 | 配置并实际调用 MCP，回应插件询问，发送图片，从历史点建立分支 | 不等于任意终端插件界面都能在网页运行 |
| D：证明并交付 | 查看同条件原版 Pi 对照结果，在实际入口完成操作，拿到使用说明、备份和回退步骤 | 小样本通过不代表所有任务都优于原版 |

阶段顺序表示优先级，不是工期承诺。先完成基线盘点，再根据实际缺口和验证成本估算工期；依赖允许的任务可交错推进，但阶段完成必须满足对应验收项。开发计划的交付与产品功能的交付分别记录。

让用户在工作台内完成开发任务时，保留固定版本 Pi 的关键能力，并获得适合网页的等价操作。优先解决长任务容易中断、历史无法接续、过程不可见、中途无法纠正，以及原版扩展能力未接入的问题。项目、资料、草稿、备份等工作台能力继续保留。

完成标准是明确范围内的功能、恢复行为和实际任务对照通过，不是“使用Pi SDK”“八项工具都在”或“测试数量增加”。不承诺未经穷尽审计的100%兼容，也不使用没有量化依据的完整度百分比。

实施时以当前会话已有授权为准。获得实施授权后按第8节持续推进，不在每个小任务结束时询问是否继续；安装、模型用量、应用等动作遵守当时会话已有授权，不重复索要已授予权限。本文不是额外安装任意第三方包或无限使用模型额度的授权。

本轮固定 Pi coding-agent/ai 1.0.3 为对照基线。需要升级时单独记录原因、接口差异和回归范围，不在补齐期间顺手升级依赖。当前工作树有未提交改动，实施前必须核实文件摘要和改动归属，不能只以HEAD判断基线。

### 必须区分的三种循环

| 循环 | 本轮处理 |
| --- | --- |
| Pi模型与工具循环 | 沿用原生AgentSession，不重写；补齐被关闭或未桥接的能力 |
| 开发Agent的实施循环 | 按本计划实现、验证、修复、记录、接续，直到交付 |
| 产品内按任意目标自动验收并持续修复的调度器 | 不假装已由前两者提供；本轮提供长任务运行、可恢复状态及明确完成语义，通用自主交付调度器属于后续独立设计 |

终端主题、终端布局及按键不逐像素复刻；确认、输入、选择、通知、取消等用户能力必须提供网页等价操作。云部署、多人协作、插件沙箱、无限预算无人值守不属于本轮。

## 3. 必须保留的运行契约

1. **Pi仍负责核心执行。** 优先使用固定SDK已有压缩、重试、消息队列、会话及扩展机制。宿主负责适配、授权、核算、持久化和显示，不复制一套容易分叉的Agent实现。
2. **所有模型请求都要进入核算。** 普通回答、压缩、分支摘要、自动重试都不能绕过用量记录与取消检查。每次尝试有唯一标识；未知用量不得按零处理，也不能重放回执重复扣减。是否经过同一运行时入口须做探针，不能只看注释。
3. **任务预算不因重试清零。** 允许显式追加授权额度，保留追加前后值和原因；新建attempt、重启或模型切换不隐式获得新额度。API费用预算与订阅请求额度分别展示，不混算。
4. **运行结束不等于目标验收完成。** 保留 `Run.completed` 与 `Task.acceptance` 的区别；页面使用“本次执行结束”“待检查”等准确文案。确定性验收通过才显示对应检查通过，不能把模型自称完成当成证明。
5. **历史与用户内容保持。** 保留原始会话、资产版本、用户确认的记忆与删除语义。旧摘要或历史工具回执不能让已删除记忆复活。压缩失败不覆盖原件，分支不改原分支。
6. **环境一致性仍成立。** 插件/MCP配置与资源版本纳入执行清单和接续兼容规则；安装写锁仍等待实际执行退出。等待交互中的执行不能因界面闲置被误判为空闲。连接断开、页面关闭与取消是不同动作。
7. **不自动切换成本来源。** 原模型不可用时显示原因，不自动改用另一个账户或付费API。旧运行保存当时模型和档位，改变选择后的新运行可追踪。
8. **管理器不执行插件获取说明。** 继续分离静态元数据、信任确认、实际加载；不因增加兼容性自动开放全部目录扩展或任意MCP进程。

## 4. 分阶段设计与任务依赖

### 阶段A：基线、核算和长任务基础

| ID | 依赖 | 交付结果 | 进入完成状态的条件 |
| --- | --- | --- | --- |
| PIF-00 能力基线 | 无 | 能力清单、当前部署/代码/测试证据快照、原版对照夹具 | 每项标明事实与未验证；既有用户改动归属清楚；无破坏性检查 |
| PIF-01 运行配置与核算探针 | 00 | 共享配置契约、请求回执、模型/档位/限制UI；压缩与重试调用探针 | 普通/压缩/分支摘要/重试的实际计次路径已证明；原生工具和模型循环保持 |
| PIF-02 原生压缩 | 01 | 自动阈值压缩、手动压缩入口、进度与取消、压缩后续接 | 长上下文及溢出恢复通过；摘要请求有用量；原件保留；失败可恢复 |
| PIF-03 大会话接续 | 01；联合验证需02 | 去除不一致的2 MiB前台门槛，受控读取、校验、接续和恢复 | 在支持容量内，能备份的有效历史不因任意更小门槛拒绝接续；主服务保持响应 |
| PIF-04 长任务额度与状态 | 01、02、03 | 长任务配置、剩余额度/时间、等待/到期/停止/恢复入口 | 超过旧5分钟边界仍能在新授权内继续；到期保存可用历史；无预算绕过 |
| PIF-05 有界自动重试 | 01、04 | 临时错误策略、退避进度、取消及重试用量 | 受控429/503恢复，不重放工具写操作；401/无权限/余额耗尽不盲重试 |

**模型与思考配置。** 提供模型支持的档位选择，新任务采用固定Pi推荐默认（当前基线通常medium），不把off冒充自动。对不支持的档位明确提示实际采用值，保存到Run并核对真实请求。旧记录保留原配置；不能更新历史policy伪造曾使用高档位。模型切换时同时检查视觉能力、档位、上下文和输出限制。API输出上限单独可配置并验证；订阅不支持的字段不能照搬。

**压缩与历史文件联合处理。** 项目摘要继续用于项目语义，Pi压缩用于模型上下文，两者不能互相替代。原生压缩会保留历史文件，不能只打开compaction就宣布解决大历史。将校验和大文件处理移到不会长期阻塞HTTP的路径，提供取消、内存界限和容量失败行为；不把整个大文件额外复制多份到内存。对照现有备份128 MiB范围，实施探针确认可支持上限并形成容量契约；若必须调整，要统一保存、备份、恢复、接续边界并提供旧历史迁移路径，不能通过降低上限绕过本任务。

至少验证超过2 MiB、32 MiB和既定容量上限附近的有效会话；还要区分模型上下文大小与磁盘历史体积。记录校验/接续耗时、内存及期间HTTP响应，形成可复跑基线。支持范围内不得出现“备份成功但无法使用恢复历史”的静默退化。

**长期执行限制。** 将运行总时长、单次网络无响应超时、等待用户交互时间分开。普通与长任务配置在一个可理解的设置入口管理；正常工作不能仍被固定5分钟阈值截断。新的长任务档位至少支持30分钟，作为明确选择而非无提示扩大旧授权；请求/费用上限独立设置，并显示剩余量。旧任务沿用既有授权。等待用户期间不继续消耗模型请求，必须有可配置等待期限、取消和恢复策略，不能永久占锁。

预算达到上限时保存检查点并展示“追加额度后继续”或“结束任务”；自动恢复只针对已确定未执行或可幂等的动作。工作进程消失、工具副作用未知时仍先对账。当前全局串行执行不要求在本轮改为多Agent并行，但一个未对账任务阻塞队列时，原因和解除入口必须清楚。

**重试策略。** 优先恢复Pi的Agent级重试，避免provider与宿主双层重试相乘。默认最多3次自动重试，尊重有上限的Retry-After/退避，仍受任务总授权约束；取消立即终止等待。错误分类、部分输出、工具调用已开始及未知响应分别处理。不会重试整个任务来代替单次临时请求恢复。

### 阶段B：过程可见与执行中可控

| ID | 依赖 | 交付结果 | 进入完成状态的条件 |
| --- | --- | --- | --- |
| PIF-06 流式过程 | 01 | 文本增量、工具进度/结果、压缩/重试状态、断线重放 | 刷新和重连不丢不重；工具调用实例可追踪；长输出有完整来源 |
| PIF-07 中途引导 | 04、06 | steering、排队追问、停止三个独立语义与消息回执 | 用户纠正在原生允许的轮次边界进入当前run；接受/已应用/未应用状态准确 |

事件协议至少具有Run、消息/工具调用ID、事件序号、类型和时间，区分partial/final/error。浏览器复用已有共享连接；服务端批量保存或合并增量，限制高频写入与缓存体积，不为每个token独立同步写库。传输可以重放，展示与持久化必须去重。最终文本与流式文本使用同一消息身份，不能多出第二条完整回复。

工具目录与实际执行日志分开显示，能查看哪个工具正在执行、结果摘要和失败原因。对大输出采用预览加可读取的完整记录，不能沿用静默截断后冒称保存完整。只展示provider实际公开的思考摘要或事件；不推断、伪造或要求暴露模型隐藏推理。

steering按Pi原生轮次边界生效，不承诺打断正在运行的单个系统命令。发送时固定目标run和commandId；如果请求到达时run已结束，返回明确冲突，由用户选择新执行，不悄悄发送到另一任务。关闭页面、断线重发、连续纠正与取消竞争均须测试。排队追问仍沿既有会话链，不退化为项目全局最近话题。

### 阶段C：原版扩展能力与网页等价操作

| ID | 依赖 | 交付结果 | 进入完成状态的条件 |
| --- | --- | --- | --- |
| PIF-08 内置扩展与配置来源 | 00、01、05、06 | MCP、codemode、tool_search接入；资源与配置来源视图 | 显式加载固定CLI同源工厂；测试本地进程与受支持HTTP传输、工具发现和实际调用 |
| PIF-09 插件交互桥接 | 04、06、08 | confirm/input/select/notify网页桥接、命令上下文适配及兼容说明 | 需要用户输入的插件真实等待并得到正确结果；不是默认false/undefined静默降级 |
| PIF-10 图片与分支 | 02、03、06、09 | 图片附件到模型、历史点分支、会话导入导出与关系展示 | 图片内容实际进入视觉请求；分支接续正确且原件不改；导入恢复通过同等校验 |

**MCP与内置扩展。** 按本地SDK要求显式提供extensionFactories，验证session_start连接与session_shutdown清理；不要只在工具名单里加入三个名字。沿用Pi配置语义，定义用户/项目/托管配置的优先级、来源展示与覆盖诊断。提供预览后导入现有配置的路径，不直接覆盖用户独立Pi配置或复制凭据到普通配置表。

配置MCP stdio来源可能启动进程，需在用户启用时清楚说明；stdio参数结构化传递，环境仅提供必要变量。连接、取消、超时、重连和进程回收均纳入生命周期；HTTP来源核对服务身份与凭据范围。工具冲突、动态注册、deferred发现、codemode暴露、断连后的不可用状态须有验证。只加载配置中启用的服务，不以兼容之名扫描并执行所有未知配置。

**交互桥接。** 每个交互具有requestId、runId、类型、状态、允许操作及过期条件。回复核对登录、运行归属和有效状态；两页面回复只接受一次，关闭弹窗不冒充用户同意，过期回复不影响新任务。服务端保存可恢复的等待状态并避免把密码或敏感输入写进普通日志。取消或worker退出要关闭对应交互，不能留下悬空Promise。

UI兼容清单至少分基本交互、命令上下文动作、终端自定义组件三类。基本交互必须可用；fork/newSession/reload等按宿主会话/环境约束映射或明确拒绝并显示原因，不能使用SDK空实现却宣称成功。任意终端自定义组件、快捷键与主题可以标为不支持，禁止显示暗示已适配的开关。

**图片附件。** 校验实际文件类型、项目权限、数量和体积，使用Pi支持的image消息结构；资产ID与原件/派生图关联可追溯。无需把二进制图片当UTF-8文本读取。模型不支持视觉时在提交前解释，不能只让图片出现在界面。图片进入历史、重试、备份恢复和分支后仍有正确来源；新交互不得改变原生read对服务器图片的既有支持。

**会话分支。** 支持用户选定可分支历史点，建立新话题并展示父子关系；原话题和未选分支保留。接续前仍核对模型、授权、插件/MCP环境及未知操作。保留已删除记忆不复活的现有语义，并展示必要的历史上下文变更说明。首次不承诺复制原版完整终端树界面，但必须有真实分支能力、历史定位、原件导出与经过校验的导入。

## 5. 接口、数据与迁移要求

预计影响 `server/pi-adapter.ts`、`worker.ts`、`scheduler.ts`、`native-session.ts`、`model-access.ts`、`service.ts`、共享contracts和主聊天页面。先定义共享契约，再接通实际通路；禁止为了赶进度引入只在前端存在的配置。

PIF-01输出ADR，固定运行配置、请求用量、事件序号、交互请求及会话兼容字段的schemaVersion和迁移规则。新增字段对旧Run应能明确回退到当时已知配置；未知不能补成“默认已开启”。查询历史不能触发安装、联网修复或额外模型请求。

数据库写入与会话文件不是一个原子事务，需要保存操作意图、提交状态及恢复依据。进程在文件写入前、写入后但数据库提交前、提交后但客户端未收到响应三个边界中断都必须能对账，不盲重放。流式消息、交互答复、追加预算和分支创建分别定义幂等键。

模型用量、资源容量和会话存储容量分别核算。新增日志、图片派生文件、流式缓存、MCP临时文件纳入容量及清理规则；清理不能删除用户源目录、未确认归属路径和需要恢复的历史。

## 7. 与原版Pi的对照方法

对照使用本地固定1.0.3 CLI，不比较不断变化的最新版。两侧分别使用干净的同源项目副本、同一模型/账户类型、思考档位、输入目标、工具/资源与授权范围。原版自动发现的额外资源要盘点并控制；工作台必需的附加上下文记录为已知差异，不假称提示完全相同。不要让两侧同时修改同一个目录。

确定性测试负责故障、协议与恢复，真实模型负责最终效果。至少包含三类真实配对任务：多文件代码修改并通过预先指定检查、长历史后继续完成原目标、图片或外部工具辅助任务。MCP、交互插件和中途纠正仍要各自完成PIV验收，即使不全纳入同一真实模型样本。

执行真实对照前先固定评分标准和调用上限，写明总预算；不得为了追求一次好结果无限重试。第一轮每类各一对完整结果，有异常或结果差异时在剩余预算内做预先记录的复验。小样本只能证明这些场景，不推广为普遍优于原版。

主要指标是独立检查是否通过、关键要求是否遗漏、是否需要额外人工介入、恢复是否成功；同时报告请求次数、tokens/已知费用、耗时及失败原因。原版能完成而工作台因适配缺口失败，必须修复后重验；两侧都失败也不能算通过。模型随机质量差异与可复现的功能缺口分开处理，不以调低验收标准解决差异。

## 8. 开发Agent的持续执行LOOP

实施入口：本文 → 联合复查 → `dev/current.md` → `dev/backlog.md` → 当前能力清单/ADR → 实际代码及运行状态。历史测试数、PID、版本和“已部署”描述均须核实。

```text
while 本计划交付条件未满足:
    读取用户最新约束，核对现场、未结束命令和证据有效性
    选择依赖就绪的PIF任务或当前失败
    定义本轮可观察结果、改动范围和PIV验收方法
    实现一个贯通改动或可证伪探针
    运行受影响检查，复核diff、迁移和失败路径
    失败则记录根因假设并修复，不跳过验收
    保存证据 → 更新唯一台账 → 更新current
    有局部阻塞则推进独立任务
    工程任务齐备后执行原版对照、实际应用和交付检查
    任一必做门槛未通过则回到循环
```

每轮必须产生代码、验证证据或被排除的假设之一。连续两轮只重复阅读或计划时缩小实验；同根因三次无进展必须改变诊断方式，不能只延长超时、改名清零或删除测试。验证通过后没有新变更则不反复重跑同一全套或真实模型。

每轮及上下文压缩/退出前保存：

```text
LOOP编号 / PIF任务 / PIV验收：
用户约束与授权范围：
工作区、分支、HEAD、未提交文件与归属：
实际改动与关键决策：
验证命令、退出码、代码摘要、证据位置：
缺陷ID、已尝试方法与被排除假设：
仍运行的会话句柄、进程身份、日志位置：
副作用操作ID及已知提交状态：
已消耗模型额度及剩余预算：
下一条具体动作与预期观察：
阻塞条件、解除方式、可独立推进项：
```

恢复先查询原命令和操作结果，不能因暂时没有输出或观察超时启动第二份。文档不自动唤醒Agent，也不保证平台无限执行；环境中断后从检查点接续。只有完成、用户明确暂停或确实没有可推进路径时结束执行，不以“是否继续”替代已经授权的工作。

所有验证使用独立数据目录、会话、插件/MCP来源和端口。测试用自编可审查服务及插件，不把用户真实项目作为破坏性夹具。证据根建议 `output/dev-evidence/pi-parity/<loop>/`，日志不包含凭据、敏感输入或完整带令牌地址。

## 9. 最终交付与Definition of Done

实施时重新核实脚本与Node要求，当前基线为Node24及 `npm run build`、`npm test`、`npm run probe:pi`、`npm run test:workbench-ui`。新增能力的验收脚本纳入可重复入口，不只留一次性手工操作。最终运行必要全套与受影响浏览器检查；上轮211项不是本轮预先通过的证据。

全部满足才能宣布本计划完成：

- PIF-00–12任务通过，PIV-01–18有与当前候选对应的证据，无未关闭阻断项。
- 能力清单明确原生保留、等价适配及真实限制；所有本轮必做差异均已关闭，不将缺口悄悄改成“后续可选”。
- 用户从主界面可以配置、启动、观察、纠正、回应插件、停止、恢复及检查结果，不依赖Agent手工修改数据库或配置文件。
- 长上下文、大历史、MCP、交互、图片、分支和原版对照均有直接证据，旧数据与原生工具无未解释回归。
- 在约定环境应用后核对源码/构建摘要、服务身份、实际入口和原业务数据摘要；原文件、配置及业务备份可定位。
- 使用说明解释“运行结束”和“验收完成”、额度/时间、等待输入、兼容边界和恢复路径；诊断信息不向普通用户堆砌SDK术语。
- 台账、current、能力清单、ADR、验收和最终报告一致；改动未提交时明确用文件摘要标识，不伪造新commit。

应用前检查在途运行、等待交互和MCP/插件进程，沿既有正常停止与启动流程。准备代码、配置、数据分别恢复的步骤，验证旧版本是否能读新结构；不能把代码回退当作数据回滚。未获实际应用或真实模型验证授权时完成可独立工作并明确阶段性交付，不能假报全部完成。

最终答复提供实际入口、已补齐能力、原版对照结果、验证范围、剩余限制和恢复材料。用户体验认可单独记录，不用用户尚未反馈掩盖已知功能缺口。
