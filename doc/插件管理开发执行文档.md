## 1. 执行入口、优先级与完成边界

收到“按本文实施”“继续插件管理开发”等指令后，Agent 按第 9 节循环持续推进依赖就绪的任务，直到第 12 节交付条件满足。每完成一个小任务不再询问是否继续。当前用户要求是编写文档，不能据此自动安装插件、修改运行服务或启动功能实现。

最新用户指令、适用的 AGENTS.md 和工具约束优先。本文定义插件功能范围；窗口行为遵循《工作台骨架重构开发执行文档》，视觉遵循当前 `design.md`。不因历史 M0/M1 标签阻止本次已授权工作，也不将历史未验收项改写成通过。

阅读顺序：本文 → `dev/current.md` → `dev/backlog.md` 的 PLG 条目 → 最近关联迭代/ADR → 实际代码。历史行号、版本、PID、测试数量均须重新核实。

完成必须包含可操作页面、真实 SDK 接入、失败恢复、当前代码对应的验证证据及约定环境的可访问交付。只有页面截图、构建通过、mock 数据或本地样例成功，都不足以宣布整个功能完成。

普通实现、修复和隔离环境验证在实施授权内持续执行。付费、对外发布、删除用户数据、安装指定第三方代码或变更真实运行环境，按当前会话已有授权判断；不重复索要已有授权。确有缺失授权时，完成可独立推进的部分，并把具体待执行动作和原因写清。

## 3. 首版范围与用户行为

### 3.1 必须交付

- “添加窗口”与设置均可打开或定位插件管理窗口，支持停靠、浮窗、收起及布局恢复。
- 当前工作台实例统一管理；管理窗口不绑定顶部当前项目。切换项目不改变全局插件配置。
- 安装 npm、Git、服务端本地路径；展示解析后的来源、版本/提交和资源清单。
- 包级启停及支持类型的资源级开关；手动更新、指定版本变更、卸载与可读错误。
- 区分已安装、已启用、待首次验证、最近加载结果；加载结果关联项目、Run、时间和环境修订。
- 真实对话能使用受支持插件能力；执行详情能查本次实际插件与资源集合。
- 操作进度可刷新恢复，关闭窗口不取消后台操作；多窗口/多浏览器状态最终一致。
- 官方包目录外链；检索当前已安装包。内嵌市场搜索不属于首版。

### 3.2 首版能力矩阵

| 资源 | 承诺 | 验收边界 |
| --- | --- | --- |
| 工具扩展 | 支持注册、许可、调用、错误、取消相关行为 | 至少一个真实工具调用；与原生/业务工具同名不得静默覆盖 |
| 事件扩展 | 支持已验证的无终端依赖生命周期 | session_start、资源发现、退出清理及异常传播有样例 |
| Skills | 保留原生发现，接入包内 Skills | 发现与实际调用分开验证，展示来源和是否受页面管理 |
| 提示词模板 | 参数展开及发送路径可用 | 带参数模板真实验证；宿主上下文不能混成用户参数 |
| 扩展命令 | 支持经验证的非交互命令分派 | 命令冲突和上下文传递有测试；依赖终端交互则标记不支持 |
| 终端 UI、Pi 主题 | 显示资源及兼容说明 | 不冒充网页主题；不提供暗示网页可用的开关 |

包可能同时包含支持与不支持的资源，因此不能仅以包为单位标注“完全兼容”。无法静态判断时显示“未验证”，不能猜测通过。P1 输出能力探针结果；若发现必做能力不可行，记录明确缺口及替代方案，不悄悄降为“提供说明即可”。

不包含插件沙箱、多人插件治理、自动更新、云同步、插件市场发布、任意旧版本并行运行、任意终端 UI 的网页仿真。不得为缩短工期删除既有 Pi 工具、技能发现或旧业务入口。

## 4. 运行与版本契约

### 4.1 环境与配置

工作台使用专属托管安装目录，不修改用户独立 Pi 的全局配置。插件配置以工作台数据库记录为唯一权威；Pi settings 为适配投影，不成为第二套可独立编辑的权威数据。

至少保存：schemaVersion、配置 revision、环境 revision、包规范化身份、请求来源、解析版本/commit、启用资源、兼容状态、操作 ID。配置开关与文件环境修订分开，以便准确描述“配置改变”和“安装内容改变”。具体类型在 PLG-01 的 ADR 中固定。

运行清单记录实际解析的包、资源、工具来源及配置/环境修订。环境修订是标识和一致性检查，不代表不可变代码副本。npm 版本之外的依赖变化也必须更新环境修订；必要时记录安装锁文件摘要。

### 4.2 整个环境读写互斥

- 启动执行前取得环境读租约；租约持有到 worker 真正退出并完成必要对账。
- 所有托管安装、更新、卸载取得同一环境写锁；新增包也可能改共享依赖，不得例外。
- 写操作进入等待后暂停新 Pi 执行的启动，允许提交并排队；已有执行正常结束或由用户主动取消，不能强杀以方便安装。
- UI 显示等待原因和占用执行；关闭页面不释放后台锁。防止新任务不断进入导致写操作饥饿。
- 服务异常重启先核对 worker/安装进程身份；仅数据库状态或 PID 不足以证明占用已释放。
- 文件处于半安装或未知状态时环境不可用于新执行，必须先对账；无插件依赖的其他业务可继续。

### 4.3 排队、重试、接续

首版采用“实际启动时固定环境”：普通排队任务在取得读租约后，原子保存本次运行清单与许可，再创建 worker。提交时只记录意图，不承诺当时环境永久可用。界面写“后续开始的执行使用新配置”，避免含糊的“下次生效”。

重试沿用原任务预算与授权语义。原执行已有插件清单时，启动前必须核对环境和工具集合；环境变化则拒绝静默重试，提供明确原因及按当前配置创建新执行的路径。启动前即失败、尚无清单的任务按首次启动处理。不得借环境变化重置同任务预算。

会话绑定增加插件清单/兼容信息。首版对插件集合或版本变化采用保守兼容规则：明确提示旧会话不能直接按原环境接续，提供新会话入口并保留历史；不能自动加载缺失旧代码或伪称无损续接。无变化的接续必须通过原生会话验证。既有无插件历史记录须有兼容迁移规则。

服务端本地路径是开发资源，文件可被外部修改，环境锁不能保护外部写入。显示“开发路径，内容可能变化”，启动时检测并记录内容变化；不承诺可复现。卸载仅移除登记，不删除源目录。旧执行恢复发现变化同样不得静默替换。

### 4.4 加载、工具与原生资源

会话阶段只读已解析资源，缺失或校验不符明确失败，不调用可能自动安装缺包的默认路径。PLG-01 用实际 SDK 验证可行的资源解析/loader 适配方式，而非假设存在某个参数。

显式绑定扩展生命周期，捕获加载和事件错误，完成退出清理。已启用资源加载失败首版阻止该次执行并显示原因，不悄悄跳过后继续生成可能错误的结果。

建立“工具来源＋工具名”目录，在初始和动态注册阶段检查冲突、生成许可并记录调用。保持原生工具和业务工具原有授权，不允许同名静默覆盖。扩展工具由扩展执行，不得错误地全部发送给只认识业务工具的宿主 RPC。

原有 `.pi`、用户/祖先 `.agents/skills` 等自动发现行为需盘点并展示来源，区分托管包、项目资源、用户资源与内置资源。页面只对其拥有管理权的资源提供开关；同名冲突必须可见。不能为做到“只有托管资源”而无声禁用用户现有 Skills。可执行扩展的启用仍受明确管理，不能自动放开项目目录里的任意扩展。

## 5. 安装生命周期与恢复

### 5.1 安装是代码执行入口

Pi 安装可能执行 npm lifecycle 脚本，信任说明必须出现在安装动作之前。首次安装默认不启用，但不能把未启用表述为尚未执行代码。可信扩展模式不是 OS 沙箱，工具许可不限制扩展直接调用系统 API。

安装在独立管理 worker 执行，使用明确的 Node/npm/Git、工作目录和最小必要环境，不继承无关凭据。禁用交互等待，设置超时、日志上限和经验证的进程树终止方式。参数使用结构化参数传递，不拼接 shell。支持含空格的 Windows 路径。不要在主服务中 import 扩展来读取说明；元数据读取与加载验证分开。

### 5.2 状态机与一致性

建议操作阶段：`queued → waiting_for_environment → preparing → applying → committing → completed`；异常进入 `failed` 或 `reconcile_required`。`failed` 只用于已知环境状态，无法确认文件状态必须对账。

每个操作持久化 operationId、幂等键、目标身份、预期修订、阶段、前后状态及错误摘要。相同请求重放返回原操作，不重复安装。API 写入沿用身份验证、同源要求和 revision 冲突检测。

包管理器文件操作与 SQLite 不具备跨介质事务。先记录意图，在锁内操作，校验结果后提交新有效配置/环境修订；失败时不声明旧环境仍正常。重启按阶段和实际目录对账，识别未登记安装、配置指向缺包、半更新。不得盲目重试未知结果。

首版允许“环境暂不可用，需按锁定来源重新安装”的恢复结果，但必须可操作且保留错误证据。只有备份和还原实际验证通过，才称为回滚；不能把重新联网安装称为原子回滚。重新安装仍可能执行脚本，沿用相同授权与进程规则。

### 5.3 备份、容量与本地源

首版备份保存包声明、锁定版本/commit、开关与相关运行记录，不默认打包 node_modules。恢复到干净目录后显示“待重新安装”；本地源缺失显示“需重新定位”。恢复和会话启动均不得自动联网补装。

托管包、缓存、临时安装及日志纳入容量统计。安装前检查可用空间与预留，超限中断进入可恢复状态；清理仅针对确认归属的暂存路径，并与安装锁、备份维护协调。不得删除本地源或未知目录。

## 6. 页面与数据通路

页面沿用工作台视觉，顶部放已安装搜索、安装入口和官方目录外链；主体采用插件列表与详情区。窄窗改为列表/详情切换，避免压缩成不可操作的双栏。

列表呈现名称、版本、来源、资源类型、启用状态和最近验证结果；详情呈现资源开关、能力限制、操作日志、错误与修复入口。不在常规产品流程堆放 SDK 类名或内部实现术语。

设置与添加窗口共用 `openOrFocusPluginManager` 等价能力。若已存在，定位所属空间或恢复收起的全局浮窗；布局复制/导入处理重复实例，保留一个可达管理窗口。实际落实 registry 策略，不能只声明 `single` 字段。

后端提供列表、详情、资源配置、安装/更新/卸载操作与进度查询，具体路径在接口契约中定稿。前端复用共享连接，插件事件驱动重新查询，不能仅发送 SSE 而没有订阅端更新。操作进度按 ID 恢复，断线重连重新拉取权威状态。

表单明确“服务端本地路径”，展示解析路径；Git/npm 缺失、网络错误、来源不存在、重复包、固定版本不可更新分别解释。所有写按钮有进行中状态及重复点击保护。失败不清空用户输入。

## 8. 验证环境与证据

测试使用独立数据目录、插件目录、端口和明确可终止的进程；不把用户真实项目当破坏性夹具。不要把未授权第三方安装混入普通单元测试。可先用自己编写的可审查样例验证协议，再在已授权范围内验证真实包来源。

证据放在 `output/dev-evidence/plugins/<轮次>/`，包含代码 commit/相关文件摘要、命令、退出码、测试结果和必要的浏览器截图。密钥、完整凭据、带 token 的来源 URL 不进入日志或提交。历史证据保留，代码变化使其失效时标记重验范围。

离线协议样例、真实 SDK、真实联网包安装、真实模型调用、浏览器交互、用户体验认可分别标注；不能互相替代。真实模型请求使用当前已配置额度和授权，遵循现有预算；外部条件缺失时完成其余工作并保留明确未验收项。

## 9. Agent 长时间工作 LOOP

### 9.1 启动与接续

1. 读取最新指令、current 和 PLG 台账，检查 Git diff，保留用户改动。
2. 核实上轮命令结果、仍运行的测试/安装/服务及其身份，避免重放有副作用动作。
3. 对照验收缺口选择一个依赖就绪任务，确定可观察结果和相关验证。
4. 先恢复未完成操作或修复当前失败，再扩展新功能；不从 PLG-00 重做已验证部分。

### 9.2 主循环

```text
while 交付条件未全部满足:
    吸收用户新反馈，核实现场和当前证据
    选择当前缺陷或依赖就绪的 PLG 任务
    定义本轮可观察结果、影响范围和验收方法
    实现最小但贯通的改动
    运行受影响检查，检查 diff 与需求覆盖
    if 失败:
        记录稳定 failureId、复现、假设和证据
        修复并重验；同根因三次无进展则改变诊断方法
    else:
        更新有效证据、台账和接续现场
    if 某项外部阻塞:
        记录解除条件，继续其他可做任务
    if 工程任务通过:
        执行完整验收、实际应用和交付检查
        任一失败则建立修复项，回到循环
    仅在完成、用户暂停或确实无可执行路径时结束
```

每轮必须产生代码、验证证据或被排除的假设之一。连续两轮只有重复阅读、计划或同一命令，下一轮必须缩小复现并提出可证伪诊断。不能删测试、降验收标准、改名清零失败次数或将未知标成通过。

测试按风险选择，失败修复后重跑受影响范围；相关检查通过且没有新变更时不反复重跑全套。最终交付前按第 10–12 节完成必要全套检查。

不要每完成一个任务就以“要不要继续”结束。等待可选反馈不阻塞独立工作。进展更新说明新事实、未确定点及下一步；长期工作不超过约 60 秒无简短进展信息，长命令用可轮询方式运行。

子 agent 仅在当时用户或适用规则明确授权时使用。此前一次审查授权不等于无限委派。若使用，分配清晰只读/写入范围，主 Agent 负责整合、复验及最终交付；不能以子 agent 自报完成代替验证。

### 9.3 状态与记录

- `dev/backlog.md`：唯一任务状态，todo/ready/doing/verifying/done/blocked/cancelled，记录依赖和验收证据。
- `dev/current.md`：目标、主任务、代码基线、已有改动、进程身份、最后结果、下一条动作和真实阻塞。
- `dev/iterations/`：每个可验证单元的实现/失败/修复记录，编号不与现有文件冲突。
- `doc/adr/`：配置权威、环境锁、接续及 loader 等关键决策。

依赖满足才 ready；已有可验收产物才 verifying；该项所有通过条件有当前证据才 done。发现回归重开任务，保留旧记录。blocked 必须写具体不可得条件及解除方式，不能笼统写“等确认”。若使用平台 goal 工具，另遵守其状态规则，不用文档状态替代平台规则。

每完成可验证单元或即将中断时保存以下模板：

```markdown
### LOOP-<编号>：<可观察结果>
- 主任务 / 验收：PLG-xx / PVxx
- 开始基线：分支、commit、相关未提交文件
- 本轮目标与影响范围：
- 实际改动 / ADR：
- 验证：命令、退出码、通过/失败/未运行、证据路径、代码摘要
- 缺陷：failureId、累计尝试、复现、已排除假设、下一诊断动作
- 仍运行的进程：用途、身份、启动命令、日志位置
- 状态及依据：
- 下一条具体动作及预期观察：
- 外部阻塞与解除条件：无 / 具体条件
```

文档不具备自动唤醒 Agent 的能力。会话内持续循环，上下文压缩后读取现场继续；进程退出、额度或工具中断后由环境或用户重新启动。不能宣称已建立后台无人值守调度。恢复时先检查已启动操作，不重复安装、迁移、模型请求或停止历史 PID。

### 9.4 每轮执行门槛

采用 Observe → Select → Define → Implement → Verify → Review → Record → Continue。循环次数不是进度；已关闭的验收缺口才是进度。

| 步骤 | 必须产出 | 进入下一步的条件 |
| --- | --- | --- |
| Observe 观察 | 当前代码、未完成命令及证据有效性 | 已区分历史事实、当前事实与待核实假设 |
| Select 选择 | 一个主要任务及其依赖 | 输入就绪；有阻塞则选择独立可推进项 |
| Define 定义 | 可观察结果、改动边界、验证方法 | 能明确说明什么结果会推翻本轮方案 |
| Implement 实现 | 一个可验证的完整改动或最小诊断实验 | 产物可检查，未扩大约定范围 |
| Verify 验证 | 命令、退出码、实际结果及证据 | 命令已结束；运行中不能算通过 |
| Review 复核 | 需求覆盖、失败路径、回归和 diff 检查 | 缺陷已修复或形成明确未完成项 |
| Record 记录 | 台账状态、现场摘要、下一条动作 | 新 Agent 可只读这些记录继续工作 |
| Continue 继续 | 下一依赖就绪任务或最终交付检查 | 未满足完成条件则继续，不以汇报替代工作 |

一轮默认只维护一个主任务；独立读取和检查可以并行。预计耗时较长的命令保留会话句柄、日志位置和启动时间，轮询原命令结果，不因暂时没有输出启动第二份。验证失败回到当前任务，不能把失败遗留给下一个阶段后仍标记 done。

### 9.5 上下文与中断恢复检查点

在开始安装、迁移、模型调用、服务切换等有副作用的动作前，以及验证完成、切换任务或上下文即将压缩时，更新检查点。写入遵循“先保存证据，再更新任务状态，最后更新 current”的顺序；若记录中途被打断，以代码、运行进程和证据复核结果为准。

检查点至少保存以下内容，不能只写“继续上轮工作”：

```text
目标与本轮用户约束：
工作区绝对路径、分支、HEAD、未提交改动归属：
当前 PLG 任务与尚未满足的 PV 验收项：
已完成且仍有效的证据：
当前失败 ID、已试方法、被排除的假设：
未结束命令的会话句柄、进程身份、日志、预计结果：
有副作用操作的操作 ID、请求摘要、已知提交状态：
下一条具体动作及通过/失败后的分支：
阻塞项、解除条件和可独立推进项：
```

恢复顺序固定为：读最新用户约束 → 核对工作区 → 查询原命令或操作结果 → 核对当前文件与证据 → 修正台账 → 执行下一条动作。对结果未知的写操作先查询，不能当作失败直接重放。不要依赖对话摘要里的旧 PID、旧测试数量或“已完成”描述替代现场核实。

外部条件阻塞时记录需要谁提供什么、如何验证条件已满足；仅该任务进入 blocked。不存在独立可推进项时可以如实结束当前执行并交代恢复入口，不能编造成功，也不能无期限轮询同一不可变条件。平台额度或执行时限到达时保存检查点，不因此降低交付标准。

### 9.6 可执行任务卡与失败收敛

任务卡写入既有台账或对应迭代记录，不另建一套状态系统。开始实现前用下列字段把大任务缩小成能独立验证的工作单元：

```text
任务 ID / 对应验收 ID：
输入与依赖：依赖任务、接口或已确认事实
预期行为：在什么条件下，用户或系统能观察到什么
允许改动范围：文件/模块；需要保留的已有改动
本轮产物：代码、文档或可证伪实验
验证方法：命令/操作、预期结果、关键失败路径
完成条件：哪些证据齐全才进入 done
失败后的下一步：缩小复现、替代假设或解除条件
```

例如，PLG-03 的一个工作单元可以是“安装请求响应丢失后重试”：输入为已有幂等操作接口，产物为客户端保留请求 ID 与服务端查询路径；验证为首次请求已被接受后模拟断网，再用同一请求重试，观察只产生一个操作和一次安装。页面显示成功而没有核对后台操作数量，不满足该任务的完成条件。

每个诊断实验先写假设、预期观察和停止条件。命令超时先查询所属进程、日志和操作状态，区分慢、卡住、失败和结果未知；不能因超时直接再发一次写操作。连续三次同根因失败后，改用最小复现、接口探针或不同层级的日志验证，而不是只加长超时或重复相同改动。失败次数与已排除假设随检查点保存，跨会话不清零。

按已配置预算执行模型调用和联网验证，记录已消耗与剩余量。已完成的真实调用优先复用回执；只有相关行为变化、证据失效或缺少必做覆盖才新增调用。没有预算或权限的独立任务可以继续，不得借新任务 ID 绕过限制。

### 9.7 证据失效与交付收敛

证据有效性取决于它实际验证的代码与环境，不能仅依据“最近一次全绿”。每份记录包含相关文件摘要、运行环境、命令和完成时间；代码变更后列出受影响的验收项，标为待复验。无关文档修订不要求重跑真实模型，运行加载逻辑变化则不能沿用旧调用记录证明新逻辑通过。

所有必做功能已实现后进入收尾循环：按 PV 清单找缺口 → 修复或补验证 → 复核受影响项 → 核对实际交付候选。此时只处理验收缺口与回归，不自行扩展市场、沙箱、自动更新等新范围。新想法记入后续任务，不阻止当前约定范围交付。

最终证据必须指向同一交付候选。构建产物与源码、已验证候选与实际运行实例分别核对；存在未部署差异时明确列出。若最终检查后又修改运行代码，重验受影响项并更新候选摘要，不能继续引用修改前的通过结果。

完整交付、阶段性交付、暂停和阻塞是不同结果。完成以第 12 节为准；仅因当前轮次结束、回复篇幅耗尽、测试运行很久或实现看起来可用，均不能转为完成。文档用于约束工作方法，不能保证平台在会话结束后继续运行。

| --- | --- | --- |

| PV04 | 默认资源发现与来源展示 | 现有 Skills 保持；托管开关与实际加载一致，同名来源可追踪 |

| PV07 | 运行中新增/更新/卸载插件 | 写操作等待整个环境；新任务排队；现有执行不读到变更依赖 |

故障注入必须真的中断受控进程/引入文件状态，不仅 mock 返回异常。至少覆盖文件变更前、文件变更后配置提交前以及提交后客户端未收到响应的边界。

验收记录每项包含：当前代码摘要、操作/命令、结果、证据路径、缺口/缺陷 ID。一个测试可以覆盖多项，但必须说明实际覆盖内容。

## 11. 最终验证与应用

实施时检查 `package.json` 的实际脚本。当前候选为 `npm run build`、`npm test`、`npm run probe:pi`、`npm run test:workbench-ui`；先确认脚本使用隔离环境再运行。新增插件集成和浏览器验收纳入可重复命令，不能只留下临时手工步骤。

最终验证包括类型/构建、相关与全套回归、实际浏览器操作、真实 SDK/插件闭环、恢复场景和数据保持。只运行 smoke test 不能代替 PV01–PV18；测试成功也不等于真实服务已应用。

应用前核实目标服务身份、实际入口、在途任务、备份与迁移兼容。正常停止/重启按项目既有流程，禁止根据文档中的历史 PID 操作。应用后确认接口、页面、运行配置与构建一致，并比较既有业务数据摘要。若当前授权不含真实实例变更，完成隔离交付候选并明确剩余应用步骤，不冒称已上线。

回退说明区分代码回退、配置恢复与插件环境修复。新结构旧代码不可读时，需要配套备份；第三方安装脚本的系统副作用不能承诺自动回退。

## 12. Definition of Done 与最终交付

全部满足才可宣布插件管理功能完成：

- PLG-00–08 必做任务通过，PV01–PV18 有与当前代码对应的证据，无未关闭的阻断缺陷。
- 用户从实际入口能完成安装、启用、使用、禁用、卸载，不依赖 Agent 手工修改数据库。
- 更新互斥、重试/接续、未知安装状态和备份缺包恢复符合契约。
- 原生 Pi 能力、现有 Skills、用户数据与工作台布局没有未解释回归。
- 使用说明包含入口、支持范围、安装执行代码的含义、生效时机、失败恢复与真实限制。
- 台账、current、迭代和证据一致；未授权/未完成的真实安装、模型或应用验证不得写成通过。
- 最终答复给出交付入口、主要变化、实际验证、剩余限制及必要恢复方式。无需用户翻读进度消息才能理解结果。

用户体验认可与工程验收分别记录。可选审美反馈不阻止工程任务继续；缺失必做验证则只能报告明确的阶段性交付，不能使用“全部完成”。

最终交付记录使用以下格式，未完成项必须保持可见：

```text
交付状态：完整交付 / 阶段性交付，剩余条件为……
入口与使用路径：
交付代码：分支/commit；若未提交，记录相关文件摘要
实现范围：对应 PLG 与 PV
验证结果：命令、退出码、证据位置、对应代码
实际应用：目标实例、版本、应用后检查；未应用则明确标注
已知限制与未完成项：
恢复或回退方式：
接续入口：current 与下一条具体动作
```

## 13. 可直接给开发 Agent 的启动指令

> 按 `doc/插件管理开发执行文档.md` 实施插件管理功能。先核实当前代码和运行环境，将 PLG 任务纳入唯一台账；按文档 LOOP 持续完成依赖就绪工作、验证、修复与交付，不在小任务结束时反复询问是否继续。保留现有 Pi 原生能力、Skills 和用户数据。遇到外部阻塞先保存具体恢复条件并推进独立任务。每个可验证单元更新现场和证据；上下文恢复后从断点继续。只有满足 Definition of Done 才报告完成；未完成的真实验证和应用如实说明。授权范围以本次会话为准，不把这段指令解释为付费、发布或安装任意第三方代码的无限授权。
